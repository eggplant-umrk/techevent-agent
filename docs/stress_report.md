# 汚れた10倍のデータでの「ネタ帳を更新」の確認（2026-11-21）

本物の会社では、活動は1か月で数千件になり、雑談・重複・途中で終わる話が大半になります。今の作りがそれに耐えられるかを確かめました。直すのはまだしていません（直すべき点の案だけ）。

## 1. 今の作り（コードを読んだ結果）

- **差分で決めるのは「だれを読むか」だけ**：`pendingEmployees()`（lib/notebook.ts）は、前回から活動の最新日が変わった社員だけを選ぶ
- **読ませるのは、その人の全履歴**：`employeeMessage()` は、選んだ人の活動を期間も件数も絞らずに全部渡し、既存のカードも全部添える。活動が1件増えただけでも、その人の全履歴を毎回読み直す
- 呼び出しは1人1回（直しがあれば最大3回）で、順番に流す（並列ではない）。指示文と社員一覧はキャッシュされる
- 本物の会社では、ほぼ全員が毎週なにか投稿するので、毎回ほぼ全員の全履歴を読み直すことになる

## 5. 直すべき点の案

効果が大きい順。1・2・3・6・7は feature/notebook-diff で直した（結果は6）。4・5・8はまだ。

1. **差分だけ読む**：前回読んだ日（`notebook_state.json` にある）より新しい活動だけを渡し、既存のカードは要約と根拠の件数だけ添える。金額と時間が「全履歴」ではなく「増えた分」に比例するようになる（C の $87 → 週の増分だけなら1人数件）
2. **AI に渡す前にコードで落とす**（数える・絞るはコード、の方針どおり）
   - 雑談のチャンネル（#random・#it-help・全社のお知らせ など）を設定で除く
   - 同じ本文の重複（空白や記号をならした本文が同じもの）は1件にまとめ、件数だけ残す
   - 決まりきった投稿（typo修正・依存の更新・「特になし」「採用面接N件」の週報 など）を除く
   - 今回のデータなら、雑談・無関係・重複で約5割をAIに渡す前に落とせる。途中で終わる話はAIの判断に残す
3. **1回に渡す量の上限**：1人あたりの件数・文字数に上限を置き（例：新しい順に60件・本文は先頭200字。提案のツールの BODY_CHARS と同じ）、超えた分は次回に回す
4. **出力を減らす**：金額の大半は出力（GitHub の例で6千トークン＝$0.12）。変わらないカードは呼び出しを省き、根拠の id は追加分だけ返させる
5. **流し方**：画面のボタンで全員を順番に流すのをやめ、夜間に差分だけをまとめて流す（Message Batches API なら半額。並列にもできる）
6. **事前の金額チェック**：流す前に文字数からトークンと金額を見積もり、上限を超えるならその場で止める
7. **重複カードのコードでの検査**：保存の前に、同じ人の既存カードと根拠の重なり・テーマの近さを見て、別カードにしようとしたら差し戻す（今回は起きなかったが、差分だけ読むようにすると起きやすくなる）
8. **社員一覧を指示文から外す**：ネタ帳の更新では本人の情報だけで足りる。300人になると毎回の指示文が大きくなる

## 6. 直したあと（feature/notebook-diff、2026-11-21）

直したこと：前回以降の新しい活動だけを渡す（読んだ活動の id を記録）／AI に渡す前にコードで落とす（同じ本文の重複・極端に短い・定型文・マージされていない PR・説明がほとんどない PR・ボットのコミット・typo や依存の更新だけのコミット）／1人分の上限（新しい順に60件・2万字・本文400字、超えた分は次回）／流す前の見積もりと予算（NOTEBOOK_BUDGET_USD、既定 $1）／保存の前の重複カードの検査。
