# MVP仕様：ネタ帳Agent（v0.3）

## 変更の経緯（v0.1 → v0.2）
- 2回目のヒアリングとレビューで方針を変更した
  - 登壇者は「ぴったりの1人」より、複数の候補から選ぶことが多い
  - 依頼はSlackで相談し、1営業日以内に決まる。断られた理由はSlackに残るだけ
  - 取り組みは公開されてから知ることがある。担当は入れ替わる
  - 申請はGitHub上のチェックリストと通知がすでにあるので、優先度を下げる
  - レビュー方針：機能を増やすのではなく、1つの仕組みで複数の問題を解く。使う人にとって便利であることを最優先にする
- そのため、中心を「依頼ごとに毎回探すAgent」から「Agentが育て続けるネタ帳」に変える
- v0.1で作ったデータ・ツール・Agentのループ・コスト管理・評価スクリプトはそのまま使う
- 追記（v0.2.1）：LayerXの開発手法を参考に、カードの修正（Human in the Loop）・候補がいないときの返し方・2段の評価を追加。Claude Codeからの質問を受けて、発信済みの取り組みと確認済みカードの扱いを明文化
- 追記（v0.2.2）：候補を「自信のある候補／条件付きの候補」で3人まで並べる形に変更し、指名の依頼では本人を必ず並べる（根拠は依頼）。注意点の日付が開催日と食い違わないかの検証を追加
- 追記（v0.2.3）：使う人向けの文（要約・理由・注意点・声かけ文など）に、内部の項目名・値・id（reviewed=false、confidence、card_id、act088 など）を書かないルールと、その検証（保存前・結合テスト）を追加
- 追記（v0.2.4）：画面の引き算に合わせ、金額（今回・累計）は通常画面に出さず ?debug のときだけ表示する形に変更。記録（usage.json）と自動切り替えはそのまま
- v0.3：入口を受信箱に変更。依頼を人が貼るのではなく、受信箱（Slack・手で追加）に届いた時点でAgentが候補まで準備しておく。候補づくりは既存の「依頼 → 候補を出す」流れをそのまま使う。Slackボットとの窓口（POST /api/inbox・GET /api/inbox/{id}）を追加
- 追記（v0.3.1）：Slackの依頼チャンネルを入口にするボットを追加。「送信しない」を「送ってよいのは依頼が来たSlackスレッドへの返信だけ」に改め、結合テストの送信の判定を scripts/ まで広げた
- 追記（v0.3.2）：受信箱から届く依頼でも指名を扱う。依頼文から指名された人を Agent が読み取り、社員データに実在するかをコードで確かめる（いなければ指名なしとして注意点に書く）。結合テストに受信箱経由の指名あり依頼を追加
- 追記（本物のデータの入口・GitHub、11/21）：架空データだけでなく本物の活動からもネタ帳を作れることを示すため、開発者本人（了承済み）の公開リポジトリを取り込む入口と、DATA_SOURCE=github の切り替えを追加。既定は架空データのままで、評価・?mock・受信箱の動きは変えない

## ゴール
- Agentが社内の取り組みを読み、「誰が・何をして・どんなテーマなら話せるか」をカードにしてネタ帳にまとめ続ける
- 技術広報は、受信箱を開くかネタ帳を見るだけで、候補とテーマと声かけの下書きが手に入る（依頼が届いた時点で、Agentが候補を準備しておく）
- 結果（承諾・辞退と理由・公開）はカードに書き戻され、次の提案が賢くなる

## 1つの仕組みで解く問題
| 問題 | ネタ帳での解き方 |
|---|---|
| 未発信の取り組みが見えない | 公開前の取り組みがカードとして先に並ぶ |
| 判断が1人に集中・同じ人ばかり | 依頼はカードから選ぶだけ。カードに登壇履歴があり、偏りが一目で分かる |
| テーマが広すぎて話せない | カードには本人の取り組みから絞ったテーマ案が書いてある |
| 記録が残らない・引き継げない | 結果がカードに書き戻される |
| 発信する人としない人の差 | イベントがなくても、未発信のカードからブログを提案できる |

## 3つの動き
1. カードを作る（ネタ帳の更新）
   - 「ネタ帳を更新」ボタンで、Agentが activities.json を社員ごとにまとめて読み、カードを作る・更新する
   - 1人に複数のカードがあってよい（取り組みごと）
   - 発信済み（published.json）と照らし、発信状況を付ける
   - 作業ログに「新しく作ったカード」「更新したカード」を表示する
2. カードから選ぶ（依頼への提案）
   - 依頼が受信箱に届くと、Agentが裏で候補づくりを始める（下の「受信箱と窓口」）。サンプルの依頼を選んで流すこともできる
   - Agentはまずネタ帳を検索し、足りなければ activities.json も調べる
   - 断られる3つの理由（テーマが合わない・忙しい・予定が重なる）と偏りを確認して、候補3人をカード付きで出す
   - 指名の依頼では、より合うカードの人がいれば「代わりにこの人」と理由つきで出す
   - 「ブログのネタを出す」ボタン：未発信のカードから3枚選び、ブログにしやすい理由を付けて出す
3. カードに書き戻す（記録）
   - 承認・承諾・辞退と理由・公開を、該当カードの「打診履歴」に追記する
   - 次の提案では、カードの打診履歴を読んで判断する（v0.1の learnings はカードに統合）

### 人が直したカードの扱い（Human in the Loop）
- 技術広報は画面でカードを直せる。直したカードは「確認済み」になり、提案で優先して使う
- Agentが活動を読み直すとき、人が直した項目（要約・テーマ案・おすすめの形）は上書きしない
- 事実として決まる項目（根拠のidの追加・最新の活動日・発信状況）は更新してよい
- 新しい活動から別のテーマ案が考えられるときは、「新しいテーマ案（未確認）」として追加し、画面に印を付ける
- 新しい活動が別の取り組みなら、新しいカードを作る。確認済みの状態は外さない
- 作業ログに「確認済みカード：内容は変えず、根拠だけ追加」のように、何をしたかを出す

### 候補の出し方（自信のある候補と条件付きの候補）
- 技術広報は複数の候補から選ぶことが多いので、候補は3人まで並べる
- 自信のある候補（テーマに合い、断られる3つの理由にも大きな引っかかりがない）を先に出す
- 足りない分は「条件付きの候補」として、何が引っかかるか（忙しい・テーマが少しずれる・根拠が1件だけ・最近登壇した など）を1文で明記して並べる
- 本当に誰もいないときだけ、「見つからない理由」と「次に確認すべきこと」を返す。条件付きでも3人に届かないときも、足りない理由として同じ形で返す
- APIの返り値では、候補ごとに `confidence`（`"strong"` ／ `"conditional"`）と `caveat`（引っかかる点の1文。conditional では必須、strong では null）を持つ。自信のある候補が先、条件付きの候補が後の順に並ぶ
- 指名の依頼では、指名された本人を必ず候補に並べる。本人の根拠は依頼そのもの（`evidence_request_id` に依頼のidを入れ、`is_nominee: true`）
  - 本人が忙しい・予定が重なる・テーマが本人の取り組みとずれる場合は conditional にし、caveat に理由と代案（共同登壇やモデレーター役なら可能か など）を書く
  - 指名された本人以外は今の基準のまま（根拠がなければ並べない）

## カードの項目（data/cards.json）
- card_id、employee_id
- 取り組みの要約（2〜3文）
- 話せるテーマ案（1〜3個。本人の取り組みから絞った具体的なタイトル）
- 根拠（activity の id の一覧。実在するものだけ）
- おすすめの形（登壇／LT／ブログ）と理由
- 発信状況（未発信／ブログ済み／登壇済み）と published の id
- 最新の活動日
- 打診履歴（日付・依頼id・結果・理由）
- 作成日・更新日

- 確認状態（未確認／確認済み）と、人が直した項目の一覧
- 新しいテーマ案（未確認）：確認済みカードに対してAgentが提案したもの。採用・却下は技術広報が1クリックで行う

### 発信済みの取り組みの扱い
- 発信済みでもカードは作る。発信状況を「ブログ済み」などにし、published の id を付ける
- 「公開しました」という告知の投稿は、取り組みの根拠ではなく発信の記録として扱う。告知の投稿だけで別のカードは作らない
- 「ブログのネタを出す」ではブログ済みのカードは出さない。登壇の提案では候補にしてよい（理由に「ブログの内容をLTにしやすい」と書ける）
- 評価の「未発信20件のうち15件以上がカードになるか」には数えない

## 受信箱と窓口（v0.3）
- 受信箱（data/inbox.json、実行時のデータなので git には入れない）
  - 依頼を受け取ったら、既存の依頼と同じ形で登録し、裏で候補づくり（既存の runAgent）を自動で始める
  - 状態：準備中（processing）→ 準備済み（ready）。失敗したらエラー（error）。準備中のまま15分を過ぎたもの（サーバーの再起動など）はエラーにする
  - 候補と作業ログを保存しておき、開いたときはそのまま出す（もう一度は実行しない）。「もう一度探す」で探し直せる
  - 入口は2つ：Slack（セッション②のボット）と、画面の「手で追加」（前の「依頼文を貼る」）
  - 承認・声かけ文の下書き・結果の書き戻しは、既存の流れをそのまま使う（受信箱の依頼の id で引ける）
- 窓口（形は docs/inbox-api.md。変えない）
  - POST /api/inbox：{ text, source: "slack" | "manual", meta?: { channel, ts, user, permalink } } を受け取り、{ id } を返す
  - GET /api/inbox/{id}：{ id, status, summary?: { candidates: [{ name, confidence, reason_short }], no_fit?: { reasons } }, url } を返す。url は画面でその依頼を開くURL（?inbox={id}）
  - localhost からのリクエストだけ受け付ける（開発サーバーは 127.0.0.1 だけで待ち受ける）
  - summary の文にも内部の言葉の判定（lib/plainText.ts）をかけ、入っていた文はテーマ案に置き換えるか落とす
- ?mock では、保存済みの結果（docs/eval_latest.json → app/_client/proposals.json）を使い、受信箱に「準備済み」の依頼が並ぶ（APIを使わない）
- 受信箱の依頼の指名（v0.3.2）
  - 依頼を既存の形に変換するところで、依頼文から「指名された人」の名前を Agent が読み取る（小さな1回の呼び出し。新しい仕組みは作らない）
  - 読み取った名前が社員データに実在するかはコードで確かめる（フルネーム、または姓だけで1人に決まるとき）。決まれば既存の指名の項目に入れ、「指名された本人を必ず並べる」「代わりの提案」がそのまま効く
  - 実在しない・同じ姓が複数いて1人に決まらない・読み取りに失敗したときは、指名なしとして扱い、その理由を各候補の注意点に書く（候補がいなければ見つからない理由に書く）
- 窓口（受信箱）は送信しない。Slackへの返信は Slack ボット（scripts/slack-bot.ts）が、依頼が来たスレッドにだけ行う

## 画面（1画面）
- 一番上：受信箱。開いたときに「新しい依頼」「候補準備済み」「準備中」が分かる。押すとその依頼の候補画面が開く
- 左：ネタ帳（カード一覧）。絞り込み：未発信だけ／登壇経験なし／事業部
- 右：依頼パネル（受信箱から開いた依頼・サンプルの依頼・手で追加 → 作業ログ → 候補3人 → 承認 → 声かけ文とLT構成案の下書き → 結果の記録）
- 候補はネタ帳のカードとして表示し、カードを開けば根拠の投稿と打診履歴が見える
- 声かけ文は編集できる。送信ボタンは置かない（コピーだけ）
- 金額（今回・累計）は通常画面には出さず、URLに ?debug を付けたときだけ上部に表示する（技術広報にはお金の数字は不要なため）。記録（data/usage.json）と自動切り替えはそのまま

## 使いやすさの原則
- 新しい入力を増やさない（結果の記録はボタンを選ぶだけ）
- 候補は3人まで。理由は1行で、根拠にすぐ飛べる
- 声かけ文は自分の言葉に直して使える
- 「なぜこの人か」がカードでいつでも確かめられる


## ツール
- search_activities(query, since)：Slack・PR・週報・設計ドキュメントから取り組みを探す
- list_employees(filter) / get_employee(id)：得意分野・忙しさ・登壇回数を見る
- get_speaking_history(id)：最後にいつ登壇したかを見る
- check_schedule(id, date)：他のイベントと重なっていないか見る
- get_published(author_id)：発信済みの記録を見る
- search_cards(query, filter)：ネタ帳のカードを探す
- get_card(card_id)：カードの詳細（根拠・打診履歴）を見る
- upsert_card(card)：カードを作る・更新する（ネタ帳の更新のときだけ使う）
- draft_outreach(employee_id, theme)：声かけ文とLT構成案の下書きを作る（送らない）
- record_outcome(request_id, card_id, result, reason)：結果をカードの打診履歴に書き戻す（画面の操作から呼ぶ）
- draft_outreach は承認ボタンから呼ぶ（ループのツールにはしない）

## 判断基準（指示文に入れる）
- テーマは、本人が実際にやった取り組みと、時流（例：今セキュリティが熱い）の両方から考える
- 偏りを減らす：最近登壇した人は下げ、登壇経験の少ない人を優先する
- 断られる3つの理由（そのテーマなら自分ではない／時間的に厳しい／他のイベントと被る）を先に確認する
- 根拠にした投稿を必ず示す。根拠のない推測で人を推さない
- 使う人向けの文（要約・テーマ案・理由・注意点・引っかかる点・見つからない理由・次に確認すべきこと・声かけ文など）には、内部の項目名・値・id（reviewed=false、confidence、card_id、act088、e002 など）を書かない。人の名前・投稿のタイトル・日付と普通の言葉で書く。idは根拠の項目にだけ入れる
- 声かけは下書きまで。送るのは人
- 送ってよいのは、依頼が来たSlackスレッドへの返信だけ（受け付けたことと、候補の要約・画面へのリンク）。DM・別チャンネル・候補者本人への送信は作らない

## 承認ポイント
- Agentが自分でやる：検索する、読む、候補を考える、下書きを作る、依頼が来たSlackスレッドに受け付けと候補の要約を返す
- 人がやる：候補を選ぶ、声かけを送る、結果を記録する

## データ
- data/ のダミーデータを使う。ネタ帳は data/cards.json に保存する（社員30人・活動120件・過去イベント20件・依頼5件・申請ルール13件）
- 発信済みの記録は、実物の「直近の発信」DBの項目に合わせて data/published.json として追加する
  - 実物の項目：タイトル、URL、タグ、Author、所属事業部、公開日時、発信ジャンル（メンバーのブログ／インタビュー記事 など）、こういう方に読んでもらいたい、所属チーム
  - 実物は1,397件・発信者229人。ダミーは30〜50件でよい
- data/README.md と note_for_demo には正解が書いてあるので、Agentの入力に絶対に含めない

## 本物のデータの入口（GitHub）
- 目的：架空データだけでなく、本物の活動データからもネタ帳を作れることを示す。材料は開発者本人（梅澤 陸、GitHub: eggplant-umrk）の公開リポジトリで、本人の了承済み。ほかの人のデータは入れない
- 取り込み：`npm run import:github -- --user eggplant-umrk`（scripts/import_github.ts、APIクレジットは使わない）
  - 読むのは本人が持つ公開リポジトリだけ（fork・アーカイブ・非公開は除く）
  - 取り込むもの：リポジトリの説明と README の冒頭／本人の PR（タイトル・本文の冒頭・マージ日。マージされずに閉じたものは除く）／本人のコミットのメッセージ（マージ・依存の更新・typo など日常の作業と、PR をまとめたコミットを除き、リポジトリ×日で1件にまとめる。1リポジトリ12日分まで）／本人が立てた Issue（タイトル・本文の冒頭）
  - 取り込まないもの：メールアドレス、非公開リポジトリ、ほかの人のコメント本文。本文に入ったメールアドレス・Co-authored-by などの行は消し、ほかの人の @メンションは「（ほかの人）」に置き換える。保存前にメールアドレスが残っていないかを確かめ、残っていれば保存しない
  - 形は data/activities.json・data/employees.json と同じ。種類は既存の4つに合わせる（PR とコミットは github_pr、リポジトリの紹介と Issue は design_doc）。活動には url（GitHub の実際のページ）を足し、画面の「根拠の投稿」から元のページを開ける
  - 社員は本人1人（e001）。所属は「個人の開発（GitHub）」、得意なことはリポジトリの主な言語とトピック、登壇回数は0、忙しさは GitHub からは分からないので中くらい（3）にする
  - 出力：data/sources/github/activities.json・employees.json
  - トークンなしで動く（未認証は1時間60回まで。1回の取り込みは「リポジトリ数×2＋4」回ほど）。制限にかかったときだけ .env の GITHUB_TOKEN（読み取り専用・任意）を使う。値は表示・ログ・コミットしない
- 切り替え：DATA_SOURCE=github（lib/dataSource.ts）
  - 切り替わるのは社員・活動と、ネタ帳（cards.json）・更新状態（notebook_state.json）の保存先。どちらも data/sources/github/ に置き、架空データのカード（data/cards.json）は上書きしない
  - 依頼・過去イベント・発信済みの記録・予定は架空データのまま
  - 未設定なら今までどおり架空データ。評価スクリプトは .env に DATA_SOURCE があっても常に架空データで動く
- 最初の更新（11/21）：活動128件（リポジトリ紹介7・PR96・コミット21日分・Issue4）から未発信のカード6枚。$0.279

## 評価
- 依頼5件を流し、data/README.md の想定候補が上位3人に入るかを確かめる（評価スクリプトだけが README を読む）
- 指名の依頼（req004・req005）で代わりの人を提案できるかを確かめる
- 今の版（v0.1）で依頼5件を流した結果を before として残し、ネタ帳版の結果（after）と比べる
- ネタ帳の更新後、data/README.md の未発信の取り組み20件のうち15件以上がカードになっているか（評価スクリプトだけが README を読む）
- 辞退をカードに書き戻したあと、同じ依頼で提案が変わるか

- 評価は2段にする（LayerXの手法を参考）
  - 結合テスト：依頼5件で、根拠idの実在・送信がSlackスレッドへの返信1か所だけであること（app/・lib/・components/・scripts/ を調べ、ほかの投稿・DM・メール送信があれば不合格）・想定候補が上位3人に入るか・条件付きの候補には必ず引っかかる点の文（caveat）があるか・指名の依頼では指名された本人が候補にいるか・注意点（cautions・caveat）の日付がその依頼の開催日と食い違わないか・使う人向けの文に内部の項目名・値・idが入っていないか をコードで判定する。90%未満なら失敗
  - 日付の食い違いは提出時（保存前）にも検証し、食い違っていればAgentに差し戻す。「開催日 X」「当日 X」「X の前後3日」のように開催日として書いた日付は開催日と一致すること、別の依頼の開催日をそのまま書かないこと（最終登壇日や予定の期間など、ほかの日付は書いてよい）
  - 内部の言葉も提出時（保存前）に検証し、入っていればAgentに差し戻す。カードの保存（Agentが書く要約・テーマ案）でも同じ検証をする。声かけ文と「代わりの人を推す理由」は、入っていれば1回だけ作り直し、それでも残ればエラーにする。ブログのネタは、入っているものを出さない
  - 質の評価：テーマ案の質だけを LLM で採点し、before との差を記録する
- 最新の実行結果は docs/eval_latest.json に残し、APIを使わない確認（--offline）と ?mock の元データにする
- 受信箱は APIを使わないテスト（npm run test:inbox）で、受け取り → 準備中 → 準備済み／エラー、窓口の返す形、summary の内部の言葉、localhost の判定、指名の照合（実在する／しない／読み取り失敗）を確かめる
- 結合テストに「受信箱経由の指名あり依頼」を1件入れる（req004 と同じ内容を本文だけで送る）。判定：準備済みになる・指名を読み取って社員データで確かめる・指名された本人が候補にいる・想定候補が上位3人・根拠idの実在・内部の言葉がない・送信なし。画面の「手で追加」で実際に流した1件は --from-inbox <id> でAPIを使わずに判定できる
