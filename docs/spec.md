# MVP仕様：ネタ帳Agent（v0.2）

## 変更の経緯（v0.1 → v0.2）
- 2回目のヒアリングとレビューで方針を変更した
  - 登壇者は「ぴったりの1人」より、複数の候補から選ぶことが多い
  - 依頼はSlackで相談し、1営業日以内に決まる。断られた理由はSlackに残るだけ
  - 取り組みは公開されてから知ることがある。担当は入れ替わる
  - 申請はGitHub上のチェックリストと通知がすでにあるので、優先度を下げる
  - レビュー方針：機能を増やすのではなく、1つの仕組みで複数の問題を解く。使う人にとって便利であることを最優先にする
- そのため、中心を「依頼ごとに毎回探すAgent」から「Agentが育て続けるネタ帳」に変える
- v0.1で作ったデータ・ツール・Agentのループ・コスト管理・評価スクリプトはそのまま使う
- 追記（v0.2.1）：LayerXの開発手法を参考に、カードの修正（Human in the Loop）・候補がいないときの返し方・2段の評価を追加。Claude Codeからの質問を受けて、発信済みの取り組みと確認済みカードの扱いを明文化

## ゴール
- Agentが社内の取り組みを読み、「誰が・何をして・どんなテーマなら話せるか」をカードにしてネタ帳にまとめ続ける
- 技術広報は、依頼を貼るかネタ帳を見るだけで、候補とテーマと声かけの下書きが手に入る
- 結果（承諾・辞退と理由・公開）はカードに書き戻され、次の提案が賢くなる

## 1つの仕組みで解く問題
| 問題 | ネタ帳での解き方 |
|---|---|
| 未発信の取り組みが見えない | 公開前の取り組みがカードとして先に並ぶ |
| 判断が1人に集中・同じ人ばかり | 依頼はカードから選ぶだけ。カードに登壇履歴があり、偏りが一目で分かる |
| テーマが広すぎて話せない | カードには本人の取り組みから絞ったテーマ案が書いてある |
| 記録が残らない・引き継げない | 結果がカードに書き戻される |
| 発信する人としない人の差 | イベントがなくても、未発信のカードからブログを提案できる |

## 3つの動き
1. カードを作る（ネタ帳の更新）
   - 「ネタ帳を更新」ボタンで、Agentが activities.json を社員ごとにまとめて読み、カードを作る・更新する
   - 1人に複数のカードがあってよい（取り組みごと）
   - 発信済み（published.json）と照らし、発信状況を付ける
   - 作業ログに「新しく作ったカード」「更新したカード」を表示する
2. カードから選ぶ（依頼への提案）
   - 依頼を入れると、Agentはまずネタ帳を検索し、足りなければ activities.json も調べる
   - 断られる3つの理由（テーマが合わない・忙しい・予定が重なる）と偏りを確認して、候補3人をカード付きで出す
   - 指名の依頼では、より合うカードの人がいれば「代わりにこの人」と理由つきで出す
   - 「ブログのネタを出す」ボタン：未発信のカードから3枚選び、ブログにしやすい理由を付けて出す
3. カードに書き戻す（記録）
   - 承認・承諾・辞退と理由・公開を、該当カードの「打診履歴」に追記する
   - 次の提案では、カードの打診履歴を読んで判断する（v0.1の learnings はカードに統合）

### 人が直したカードの扱い（Human in the Loop）
- 技術広報は画面でカードを直せる。直したカードは「確認済み」になり、提案で優先して使う
- Agentが活動を読み直すとき、人が直した項目（要約・テーマ案・おすすめの形）は上書きしない
- 事実として決まる項目（根拠のidの追加・最新の活動日・発信状況）は更新してよい
- 新しい活動から別のテーマ案が考えられるときは、「新しいテーマ案（未確認）」として追加し、画面に印を付ける
- 新しい活動が別の取り組みなら、新しいカードを作る。確認済みの状態は外さない
- 作業ログに「確認済みカード：内容は変えず、根拠だけ追加」のように、何をしたかを出す

### 候補の出し方（自信のある候補と条件付きの候補）
- 技術広報は複数の候補から選ぶことが多いので、候補は3人まで並べる
- 自信のある候補（テーマに合い、断られる3つの理由にも大きな引っかかりがない）を先に出す
- 足りない分は「条件付きの候補」として、何が引っかかるか（忙しい・テーマが少しずれる・根拠が1件だけ・最近登壇した など）を1文で明記して並べる
- 本当に誰もいないときだけ、「見つからない理由」と「次に確認すべきこと」を返す。条件付きでも3人に届かないときも、足りない理由として同じ形で返す
- APIの返り値では、候補ごとに `confidence`（`"strong"` ／ `"conditional"`）と `caveat`（引っかかる点の1文。conditional では必須、strong では null）を持つ。自信のある候補が先、条件付きの候補が後の順に並ぶ
- 指名の依頼では、指名された本人を必ず候補に並べる。本人の根拠は依頼そのもの（`evidence_request_id` に依頼のidを入れ、`is_nominee: true`）
  - 本人が忙しい・予定が重なる・テーマが本人の取り組みとずれる場合は conditional にし、caveat に理由と代案（共同登壇やモデレーター役なら可能か など）を書く
  - 指名された本人以外は今の基準のまま（根拠がなければ並べない）

## カードの項目（data/cards.json）
- card_id、employee_id
- 取り組みの要約（2〜3文）
- 話せるテーマ案（1〜3個。本人の取り組みから絞った具体的なタイトル）
- 根拠（activity の id の一覧。実在するものだけ）
- おすすめの形（登壇／LT／ブログ）と理由
- 発信状況（未発信／ブログ済み／登壇済み）と published の id
- 最新の活動日
- 打診履歴（日付・依頼id・結果・理由）
- 作成日・更新日

- 確認状態（未確認／確認済み）と、人が直した項目の一覧
- 新しいテーマ案（未確認）：確認済みカードに対してAgentが提案したもの。採用・却下は技術広報が1クリックで行う

### 発信済みの取り組みの扱い
- 発信済みでもカードは作る。発信状況を「ブログ済み」などにし、published の id を付ける
- 「公開しました」という告知の投稿は、取り組みの根拠ではなく発信の記録として扱う。告知の投稿だけで別のカードは作らない
- 「ブログのネタを出す」ではブログ済みのカードは出さない。登壇の提案では候補にしてよい（理由に「ブログの内容をLTにしやすい」と書ける）
- 評価の「未発信20件のうち15件以上がカードになるか」には数えない

## 画面（1画面）
- 左：ネタ帳（カード一覧）。絞り込み：未発信だけ／登壇経験なし／事業部
- 右：依頼パネル（依頼の入力 → 作業ログ → 候補3人 → 承認 → 声かけ文とLT構成案の下書き → 結果の記録）
- 候補はネタ帳のカードとして表示し、カードを開けば根拠の投稿と打診履歴が見える
- 声かけ文は編集できる。送信ボタンは置かない（コピーだけ）
- 画面上部に「今回の金額」「累計」を表示する

## 使いやすさの原則
- 新しい入力を増やさない（結果の記録はボタンを選ぶだけ）
- 候補は3人まで。理由は1行で、根拠にすぐ飛べる
- 声かけ文は自分の言葉に直して使える
- 「なぜこの人か」がカードでいつでも確かめられる


## ツール
- search_activities(query, since)：Slack・PR・週報・設計ドキュメントから取り組みを探す
- list_employees(filter) / get_employee(id)：得意分野・忙しさ・登壇回数を見る
- get_speaking_history(id)：最後にいつ登壇したかを見る
- check_schedule(id, date)：他のイベントと重なっていないか見る
- get_published(author_id)：発信済みの記録を見る
- search_cards(query, filter)：ネタ帳のカードを探す
- get_card(card_id)：カードの詳細（根拠・打診履歴）を見る
- upsert_card(card)：カードを作る・更新する（ネタ帳の更新のときだけ使う）
- draft_outreach(employee_id, theme)：声かけ文とLT構成案の下書きを作る（送らない）
- record_outcome(request_id, card_id, result, reason)：結果をカードの打診履歴に書き戻す（画面の操作から呼ぶ）
- draft_outreach は承認ボタンから呼ぶ（ループのツールにはしない）

## 判断基準（指示文に入れる）
- テーマは、本人が実際にやった取り組みと、時流（例：今セキュリティが熱い）の両方から考える
- 偏りを減らす：最近登壇した人は下げ、登壇経験の少ない人を優先する
- 断られる3つの理由（そのテーマなら自分ではない／時間的に厳しい／他のイベントと被る）を先に確認する
- 根拠にした投稿を必ず示す。根拠のない推測で人を推さない
- 声かけは下書きまで。送るのは人

## 承認ポイント
- Agentが自分でやる：検索する、読む、候補を考える、下書きを作る
- 人がやる：候補を選ぶ、声かけを送る、結果を記録する

## データ
- data/ のダミーデータを使う。ネタ帳は data/cards.json に保存する（社員30人・活動120件・過去イベント20件・依頼5件・申請ルール13件）
- 発信済みの記録は、実物の「直近の発信」DBの項目に合わせて data/published.json として追加する
  - 実物の項目：タイトル、URL、タグ、Author、所属事業部、公開日時、発信ジャンル（メンバーのブログ／インタビュー記事 など）、こういう方に読んでもらいたい、所属チーム
  - 実物は1,397件・発信者229人。ダミーは30〜50件でよい
- data/README.md と note_for_demo には正解が書いてあるので、Agentの入力に絶対に含めない

## 技術
- Next.js（App Router）＋TypeScript
- Claude API の tool use
- モデルは2段構え。.env の AGENT_MODEL / HEAVY_MODEL で切り替えられるようにする
  - Agentのループ（検索・確認・候補の絞り込み）：claude-opus-5-5
  - 重い仕事（承認後の声かけ文とLT構成案の作成、指名の依頼で代わりの人を推す理由づけ）：claude-fable-5-2
  - Fableの呼び出しが失敗したらOpusで作り直す
- APIキーは .env の ANTHROPIC_API_KEY。サーバー側だけで使い、ブラウザには出さない
- 作業ログはストリーミングで表示する

## コスト管理
- APIクレジットは月$200が上限（カード未登録なので、使い切っても請求はされずAPIが止まるだけ）
- 使用量の記録：APIの返事に含まれる入力・出力トークン数（キャッシュ分も含む）を、料金表で金額に換算して data/usage.json に追記する
  - 料金（100万トークンあたり）：Opus 5.5 入力$4・出力$20・キャッシュ読み込み$0.20／Fable 5.2 入力$8・出力$40・キャッシュ読み込み$0.20／Sonnet 5.5 入力$2・出力$10・キャッシュ読み込み$0.10
  - 料金表はコード内の1か所にまとめ、変えやすくする
- 画面に「今回の提案：$0.42」「累計：$12.30」のように表示する
- 自動切り替え：累計が USAGE_SWITCH_USD（.env、初期値150）を超えたら、ループを Opus → Sonnet 5.5、重い仕事を Fable → Opus 5.5 に切り替え、画面に切り替えたことを表示する
- 節約
  - プロンプトキャッシュを使う（指示文・ツール定義・社員一覧など毎回同じ部分）
  - ツールの結果は短く返す（検索は上位10件、本文は要約か先頭200文字）
  - ステップ上限15回
- ネタ帳の更新は社員ごとにまとめて呼び出し、プロンプトキャッシュを使う。最初は社員5人分だけで試し、金額を確認してから全員分を作る

## 評価
- 依頼5件を流し、data/README.md の想定候補が上位3人に入るかを確かめる（評価スクリプトだけが README を読む）
- 指名の依頼（req004・req005）で代わりの人を提案できるかを確かめる
- 今の版（v0.1）で依頼5件を流した結果を before として残し、ネタ帳版の結果（after）と比べる
- ネタ帳の更新後、data/README.md の未発信の取り組み20件のうち15件以上がカードになっているか（評価スクリプトだけが README を読む）
- 辞退をカードに書き戻したあと、同じ依頼で提案が変わるか

- 評価は2段にする（LayerXの手法を参考）
  - 結合テスト：依頼5件で、根拠idの実在・送信していないこと・想定候補が上位3人に入るか・条件付きの候補には必ず引っかかる点の文（caveat）があるか・指名の依頼では指名された本人が候補にいるか をコードで判定する。90%未満なら失敗
  - 質の評価：テーマ案の質だけを LLM で採点し、before との差を記録する

## 対象外
- 実際の送信や申請、飲食の発注予測、社内データとの連携、ID連携
