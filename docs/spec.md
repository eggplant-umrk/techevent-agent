# MVP仕様：ネタ帳Agent（v0.4）

## 変更の経緯（v0.1 → v0.2）
- 2回目のヒアリングとレビューで方針を変更した
  - 登壇者は「ぴったりの1人」より、複数の候補から選ぶことが多い
  - 依頼はSlackで相談し、1営業日以内に決まる。断られた理由はSlackに残るだけ
  - 取り組みは公開されてから知ることがある。担当は入れ替わる
  - 申請はGitHub上のチェックリストと通知がすでにあるので、優先度を下げる
  - レビュー方針：機能を増やすのではなく、1つの仕組みで複数の問題を解く。使う人にとって便利であることを最優先にする
- そのため、中心を「依頼ごとに毎回探すAgent」から「Agentが育て続けるネタ帳」に変える
- v0.1で作ったデータ・ツール・Agentのループ・コスト管理・評価スクリプトはそのまま使う
- 追記（v0.2.1）：LayerXの開発手法を参考に、カードの修正（Human in the Loop）・候補がいないときの返し方・2段の評価を追加。Claude Codeからの質問を受けて、発信済みの取り組みと確認済みカードの扱いを明文化
- 追記（v0.2.2）：候補を「自信のある候補／条件付きの候補」で3人まで並べる形に変更し、指名の依頼では本人を必ず並べる（根拠は依頼）。注意点の日付が開催日と食い違わないかの検証を追加
- 追記（v0.2.3）：使う人向けの文（要約・理由・注意点・声かけ文など）に、内部の項目名・値・id（reviewed=false、confidence、card_id、act088 など）を書かないルールと、その検証（保存前・結合テスト）を追加
- 追記（v0.2.4）：画面の引き算に合わせ、金額（今回・累計）は通常画面に出さず ?debug のときだけ表示する形に変更。記録（usage.json）と自動切り替えはそのまま
- v0.3：入口を受信箱に変更。依頼を人が貼るのではなく、受信箱（Slack・手で追加）に届いた時点でAgentが候補まで準備しておく。候補づくりは既存の「依頼 → 候補を出す」流れをそのまま使う。Slackボットとの窓口（POST /api/inbox・GET /api/inbox/{id}）を追加
- 追記（v0.3.1）：Slackの依頼チャンネルを入口にするボットを追加。「送信しない」を「送ってよいのは依頼が来たSlackスレッドへの返信だけ」に改め、結合テストの送信の判定を scripts/ まで広げた
- v0.4：イベント後のアンケート（Googleフォームの CSV）をAgentが読み、登壇者のカードに書き戻す（使うほど賢くなる、をイベント後まで届かせる）。新しい仕組みは作らず、Agentのループ（検証と差し戻し）・カードの書き戻し・テーマ案の採用／見送り・内部の言葉の判定を使い回す。数字はコードで計算し、Agentには書かせない。AI は文の意味（良い点／不満・運営／内容・攻撃）と要約・テーマ・重なりだけを担当し、ネガティブは原文のまま全部、カードには事実だけを残す
- 追記（v0.3.2）：受信箱から届く依頼でも指名を扱う。依頼文から指名された人を Agent が読み取り、社員データに実在するかをコードで確かめる（いなければ指名なしとして注意点に書く）。結合テストに受信箱経由の指名あり依頼を追加
- v0.4：「カード（ネタ）→ 出し先を探す」を追加。依頼が来てから人を探すだけでなく、ネタが先で社外の出し先（CFP）を探す。既存のループ・候補の出し方・注意点の判定・ブログ提案・声かけ文を使い回し、外部イベントのデータ（data/external_events.json）と search_external_events を足した。結合テストにカード → 出し先を2件追加
- 追記（本物のデータの入口・GitHub、11/21）：架空データだけでなく本物の活動からもネタ帳を作れることを示すため、開発者本人（了承済み）の公開リポジトリを取り込む入口と、DATA_SOURCE=github の切り替えを追加。既定は架空データのままで、評価・?mock・受信箱の動きは変えない
- 追記（忙しさを予定から計算、11/21）：社員の「忙しさ（1〜5）」は架空データに決め打ちで書いてあるだけで根拠がなかったので、予定から計算する形に変更（lib/busyness.ts、AIは使わない）。使う人向けの文では「忙しさ5」のような段階を出さず「今後2週間は勤務時間の7割が予定で埋まっている」のように書く。本物のカレンダーは iCal（CALENDAR_ICS_URL）で読めるようにしたが、今はつながない
- 追記（候補の人数と経験の扱い、11/21）：候補を「3人まで」から「合う人がいるだけ、5人まで（0人なら見つからない理由）」に変更。「最近登壇した人は下げ、登壇経験の少ない人を優先する」をやめ、順位はテーマの合い方と根拠で付ける。代わりに各候補に登壇経験の印（初登壇／半年以内に登壇／登壇経験あり）をコードで付けて理由の近くに出し、選ぶのは人に任せる。結合テストの判定を「5人まで・自信のある候補が先・印あり」に変更
- 追記（デモ用の本人と印の重なり、11/21）：登壇経験の印と同じことだけを言っている注意点（「登壇経験なし（初登壇）」など）を、表示の前にコードで除くようにした（指示文は変えない）。正解データ（data/README.md）の説明を「経験で順位を下げる」前提から「印で見せて人が判断する」形に書き直した（評価の判定と想定候補は変えない）。デモ用に、開発者本人を架空の会社の31人目として入れる切り替え DEMO_PERSON=on を追加
- 追記（Slack のプライバシー、11/21）：依頼チャンネルは社内の人が見るので、候補の名前や理由（予定の埋まり具合、アンケートの反応など）を依頼した人やチャンネルの全員に見せない。依頼スレッドへの返信は受付の一文だけにし、準備ができたら技術広報だけの非公開チャンネル（SLACK_NOTIFY_CHANNEL）に画面へのリンクだけを送る。送信のルールと結合テストの判定、窓口の返す形（summary をやめる）を合わせて変えた
- 追記（画面を3タブに整理、11/21）：機能は増やさず、「いつ使うか」で受信箱・ネタ帳・アーカイブの3タブに置き直した（中身は docs/ui-guidelines.md）。ネタ帳は人ごとの画面にし、カードのない人も含めて社員全員を出す。人の情報（得意分野・登壇の意向・NGのテーマ）を画面で直せるようにし、直した項目は確認済みとして Agent は上書きしない。Agent は意向とNGのテーマに従い、「今は控えたい」の人は条件付きでしか出さず、NGのテーマに当たる案はコードで差し戻す。開催日が過ぎた依頼は、日付をコードで判定して受信箱からアーカイブへ移す。予定の埋まり具合とアンケートは、別の作業の結果が入る場所だけ用意した
- 追記（X の会話の貼り付けと主催者への返事、11/21）：登壇の依頼は X（DM・リプライ）で来ることが多く、X 上のやり取り自体がイベントの温かみになっていると分かった。X には手を出さず（読みにいかない・返信しない）、次の2つを足した
  - 受信箱の「手で追加」に X の会話をそのまま貼れるようにした。Agent が会話からイベント名・日程・形式・テーマ・指名・主催者の名前と、その根拠の一節を読み取り、コードが「一節が本当に会話にあるか」「日程が1日に決まっているか（候補日・期間・調整中は未定）」「指名が社員データに実在するか」を確かめる。確かめられない項目は「未定」として候補の注意点に書き、推測で埋めない。読み取った項目は既存の依頼の形（依頼文の先頭）に足して、指名の検証・候補づくりはそのまま使う
  - 候補を承認したら、声かけ文と同じ1回の呼び出しで「主催者への返事」（X で返す短い文、280字まで）も下書きする。送信はしない（コピーのみ）。忙しさ・予定の埋まり具合・登壇回数・アンケートの反応・ほかの候補など社内の評価に当たる情報や、社内の人への敬称はコードで検査し、作り直しても残れば決まった形の文に差し替える
  - テストは架空の X 風の会話3件（scripts/fixtures/x_conversations.ts）で、API を使わずに読み取り後の検査を確かめる（npm run test:xconv）。本物の API での確認は1回（$0.305）
- 追記（3タブにイベント後の画面と忙しさを組み込む、11/21）：アーカイブの過去のイベントを開くと、イベント後の画面（アンケートの取り込み・分析・ネガティブとポジティブ・カードへの書き戻し）が右に出る。ヘッダーの「依頼／イベント」の切り替えは3タブに置き換えた。ネタ帳の人の画面の予定欄は忙しさの計算（busynessFor / busyText）を使い、今後2週間の予定は日ごとの時刻だけを出す（タイトルは出さない）。登壇経験の言い方は候補の印にそろえた。DEMO_PERSON=on の本人もネタ帳の一覧と候補に出る（予定は iCal が読めるときだけ計算され、読めなければ「予定は不明」）
- 追記（使いやすさの直し、11/21。docs/ux_review.md）：ブログ・イベントページへのリンクに ?mock と開いていた人・イベントを付け、「戻る」でそのまま戻す。内部の id（inb-…・act088 など）は、イベント名・活動の種類とタイトルに置き換え、打診履歴は1依頼1行（声かけ → 承諾）にまとめた。候補の見出しの「・」だけの残り、中身のない「次に確認すべきこと」の見出しを出さない。「分析済み」のイベントは開いたときに保存済みの分析を出す。承諾を取り消せるようにした（POST /api/outcome/undo。その依頼の最後の記録が承諾のときだけ1つ戻す）。承諾のあとは「もう一度探す」と日程の文を出さない。?mock では「保存済みの結果を出しています」と明記。「手で追加」は「会話を貼って追加」にし、説明と「やめる」を付けた。候補の注意点は切らずに2つまで見せて「ほかN件を見る」。本番用のビルドで見せる手順（npm run build → npm run start、127.0.0.1:3000）を README に書いた
- 追記（日程の提案の画面、11/21）：日程が未定の依頼では、受信箱の候補の横に「空いていそうな日」（詳細の date_suggestions。lib/dateSuggest.ts がコードで計算）を出し、「本人に確認する前の目安です」と明記する。予定が分からない人は「予定は不明」、予定が分かる範囲の外などの補足はそのまま出す。主催者への返事の下書きには「この日あたりなら調整しやすそうです（本人に確認します）」を入れるボタンを付け、押したときだけ入れる
- 追記（人の並び順・担当者の根拠・イベントページ、11/21）：ネタ帳の人の一覧は、DEMO_PERSON=on のときデモ用の本人を一番上に固定して「本人（デモ）」の印を付け、ほかは「未発信のネタが多い順 → 最近の活動が新しい順」に並べる（コード）。カード詳細の見出しからも予定の言葉を外した（受信箱の候補と出し先の注意点では今までどおり使う）。担当者未定のネタで先頭に出す「関わっていそうな人」は、キーワードが一致した活動（根拠）がある人だけにし、その活動を横に出す。根拠がなければ誰も選ばない。イベントのデータに connpass_url を足し（gen_data.py。架空のイベントは空）、アーカイブのイベント画面に「イベントページを開く」を置いた（connpass_url があればそのページ、なければアプリの中の架空のイベントページ /events/{id}。「架空のイベントページです。本番では connpass のイベントページに飛びます」と明記し、見た目はこのアプリのまま）。受信箱の依頼の会話に connpass などのイベントの URL があれば、コードで取り出してリンクにする（会話の中に本当にある URL だけ）
- 追記（ネタ帳タブの予定を外す・担当者未定のネタ、11/21）：ネタ帳タブの人の一覧の「予定 ○割」と、人の画面の予定欄（埋まり具合の言葉・今後2週間の予定）を外した。忙しさの計算は残し、受信箱の候補と出し先の注意点では今までどおり使う。リリースノート（活動の種類 release_note）の表示名を「リリース」にし、ネタ帳タブに「担当者未定のネタ」の一覧（GET /api/unassigned-cards。リリースのタイトル・日付・公開ページへのリンク・テーマ案）を足した。担当者を選んで割り当てる（POST /api/unassigned-cards/assign）と、その人のカードになり一覧から消える
- 追記（アンケートの声の直し・保存済みの分析結果、11/21）：別の社員と重ならない声は、登壇者本人が続編として話せる（書き戻しで本人のカードにテーマ案として入る）ので、一覧でも本人とカードを「話せそうな人」として出す（どの登壇への声かは出さない）。本番の画面で分析結果のファイル（data/survey_analysis.json）がないイベントは、保存済みの分析結果（docs/survey_latest.json。架空のアンケートを本番の API で分析したもの）で補い、イベント画面とアンケートの声に「架空のアンケート」と出す。API で分析し直さない。画面で分析し直すと置き換わる
- 追記（アンケートの声と推す文の表示、11/21）：技術広報のレビューで、ネタ帳タブに「アンケートの声」の一覧を足した（アンケートの「今後聞いてみたい話」を、イベント名・日付・件数つきで並べ、「アンケートの声」のタグを付ける）。合う人がいる声は「需要あり」の仕組み（別の社員の未発信カードとの重なり）でその人とカードにつなぎ、いない声は「まだ話せる人がいない」と出す。どの登壇への声かは出さない。カードのテーマ案と「需要あり」のうちアンケート由来のもの（声と同じ文）にも同じタグを付ける。受信箱の依頼で代わりの人を推す文を作っている間（pitch_status が pending）は「代わりの人を推す文を作成中」と出し、2秒ごとに詳細を読み直してできたら表示する
- 追記（入口を受信箱に一本化・依頼の状態、11/21）：画面の「サンプルの依頼を選ぶ」欄をなくし、サンプルの依頼（data/requests.json）も受信箱に届いた依頼として並べる（自動では候補を出さず、「ネタ帳から候補を出す」で出した結果を保存する）。依頼の状態「準備中 → 候補準備済み → 声かけ中（承認した）→ 承諾済み／辞退（結果を記録した）→ 開催後」を、カードの打診履歴から人ごとの最後の記録でコードが決める（lib/requestStage.ts。AI は使わない）。辞退のあとに別の候補へ声をかけたら声かけ中に戻る。受信箱の一覧・依頼の画面・カードに状態の印を出し、承諾済みなら誰が受けたかとカードに「○○で承諾済み」を出す。承諾済みの依頼は候補の一覧の代わりに決まった人・開催日・主催者への返事の下書き（声をかけたときに保存したもの）を出す。評価用のデータと結合テストの動きは変えない
- 追記（イベント画面を overview に切り替え、11/21）：アーカイブのイベント画面はイベント単位の集計（overview）だけを使う形にした。登壇者は「誰が何を話したか」の一覧だけで、登壇者ごとの点数・不満・良い点は出さない。カード詳細の「登壇者の反応」の表示を消し（「需要あり」の提案は残す）、窓口と型から古い項目（talks・answers・sentences・analysis・TalkStats）を削除した。あわせて本人の予定（iCal）の読み取りを強くし（TZID の変換・変更された回）、取得や読み取りに失敗したときの理由をログに出すようにした（URL は出さない）
- 追記（登壇者の評価は内部だけ、11/21）：イベント画面が「登壇者の評価表」に見えるため、登壇者ごとの反応は候補を出すときの参考として Agent に渡すだけにし、画面用の窓口・Slack・下書き・カードには出さない。全体の満足度は登壇者に結びつけず（イベント単位の集計にだけ使う）、登壇ごとの点数の列があるときだけ登壇者の参考にする。登壇者の参考にするのは自由記述の「内容（登壇）」だけで、運営・会場・設備の不満は入れない。窓口にイベント単位の集計 overview を足した（登壇者ごとの古い項目は、画面を切り替えたあと同じ日に削除）
- 追記（代わりの人を推す文を後回し、11/21）：受信箱の依頼では、候補ができた時点で「準備済み」にし、代わりの人を推す文（指名の依頼だけ、重いモデルで7〜11秒）はそのあと裏で作る。状態は pitch_status（作っている／できた／作れなかった）。Slack の返信が早くなる。画面の「ネタ帳から候補を出す」は今までどおり最後まで待つ
- 追記（ネタ帳の更新を差分だけにする、11/21）：本物の会社の量（活動が月に数千件、雑談や重複が大半）に耐えるため、「ネタ帳を更新」で AI に渡すのを「前回以降の新しい活動」と既存のカードの要約だけにした（今までは選んだ人の全履歴を毎回渡していた）。渡す前にコードで、同じ本文の重複・極端に短いもの・定型文・マージされていない PR・説明がほとんどない PR・ボットのコミット・typo や依存の更新だけのコミットを落とし、件数と理由を作業ログに出す。1人分の件数と文字数に上限を置き、超えた古い分は次回に回す。流す前に金額を見積もり、NOTEBOOK_BUDGET_USD（既定 $1）を超えるなら API を呼ばずに止める。新しいカードを保存する前に、同じ人の既存カードと根拠の重なり・テーマの近さをコードで見て、重なるなら差し戻す。結果は docs/stress_report.md の6

- Agentが社内の取り組みを読み、「誰が・何をして・どんなテーマなら話せるか」をカードにしてネタ帳にまとめ続ける
- 技術広報は、受信箱を開くかネタ帳を見るだけで、候補とテーマと声かけの下書きが手に入る（依頼が届いた時点で、Agentが候補を準備しておく）
- 結果（承諾・辞退と理由・公開）はカードに書き戻され、次の提案が賢くなる

## 1つの仕組みで解く問題
| 問題 | ネタ帳での解き方 |
|---|---|
| 未発信の取り組みが見えない | 公開前の取り組みがカードとして先に並ぶ |
| 判断が1人に集中・同じ人ばかり | 依頼はカードから選ぶだけ。カードに登壇履歴があり、偏りが一目で分かる |
| テーマが広すぎて話せない | カードには本人の取り組みから絞ったテーマ案が書いてある |
| 記録が残らない・引き継げない | 結果がカードに書き戻される |
| 発信する人としない人の差 | イベントがなくても、未発信のカードからブログを提案できる |

## 動き（3つ＋イベントのあと）
1. カードを作る（ネタ帳の更新）
   - 「ネタ帳を更新」ボタンで、Agentが activities.json を社員ごとにまとめて読み、カードを作る・更新する
   - 1人に複数のカードがあってよい（取り組みごと）
   - 発信済み（published.json）と照らし、発信状況を付ける
   - 作業ログに「新しく作ったカード」「更新したカード」を表示する
   - 渡すのは前回以降の新しい活動だけ（社員ごとに、読んだ・落とした活動の id を notebook_progress.json に記録。記録がなければ notebook_state.json の日付までを読んだものとして引き継ぐ）。前回までの分は既存のカードの要約として添える
   - AI に渡す前にコードで落とす（lib/notebookPrep.ts）：同じ本文の重複（空白と句読点だけならす。数字だけ違う進み具合の報告は残す）、極端に短いもの（10文字未満）、定型文（「特になし」など）、マージされていない PR、説明がほとんどない PR、ボットのコミット、typo・依存の更新・書式だけのコミット（1日のコミットのまとめは、中身のあるコミットだけを残す）。落とした件数と理由は作業ログと notebook_progress.json に残す
   - 1人分の上限：新しい順に60件・2万字・1件の本文400字まで（.env の NOTEBOOK_MAX_ITEMS・NOTEBOOK_MAX_CHARS・NOTEBOOK_BODY_CHARS で変えられる）。超えた古い分は「読んだ」にせず、次回に回す
   - 流す前に金額を見積もる（依頼文は1字0.8トークン、キャッシュする指示文はそれにツールの定義 約1千トークンを足す。出力は1回 約1千トークン＋渡した活動1字あたり0.16トークン。Opus 5.5 は考える分も出力に数えるので、活動が少なくても1回 約1千トークン出る。記録した回との比べ方は scripts/check_notebook_estimate.ts）。NOTEBOOK_BUDGET_USD（既定 $1）を超えるなら、API を呼ばずに理由を出して止める。流している途中で今回の金額が上限に届いたら、残りの人は次回に回す
   - 新しいカードを保存する前に、同じ人の既存カードと根拠が重なるか、テーマ・要約が近い（2文字ずつの重なり6割以上）なら差し戻し、card_id を指定して更新するよう伝える
2. カードから選ぶ（依頼への提案）
   - 依頼が受信箱に届くと、Agentが裏で候補づくりを始める（下の「受信箱と窓口」）。サンプルの依頼を選んで流すこともできる
   - Agentはまずネタ帳を検索し、足りなければ activities.json も調べる
   - 断られる3つの理由（テーマが合わない・忙しい・予定が重なる）を確認して、合う候補を5人までカード付きで出す（登壇経験の印付き）
   - 指名の依頼では、より合うカードの人がいれば「代わりにこの人」と理由つきで出す
   - 「ブログのネタを出す」ボタン：未発信のカードから3枚選び、ブログにしやすい理由を付けて出す
3. カードに書き戻す（記録）
   - 承認・承諾・辞退と理由・公開を、該当カードの「打診履歴」に追記する
   - 次の提案では、カードの打診履歴を読んで判断する（v0.1の learnings はカードに統合）
4. イベントのあとに書き戻す（v0.4）
   - 入口：Googleフォームの回答をスプレッドシートから CSV で書き出したもの。画面の「イベント」で過去イベントを開き、CSV を選ぶか貼ると取り込める。Google への API 連携は作らない
     - 列の意味（どの登壇か・満足度・感想・次に聞きたいテーマ・職種）は、まず質問文のキーワードでコードが決める。決まらない列だけ Agent に聞く（渡すのは質問文と、個人情報を伏せた見本の値だけ）。読み取れない列は無視して画面に出す
     - 個人を特定できる列（メール・名前など）は取り込み時に捨てる。保存も Agent への受け渡しもしない。自由記述の中のメール・電話番号は伏せる
     - カジュアル面談の希望（11/22）：質問文に「カジュアル面談」「面談」「話を聞いてみたい」「採用」がある列を、コードだけで面談の希望の列とする（Agent には聞かない）。値は はい／いいえ に読み替え（「希望しない」などの否定を先に見る。読めない値は数えない）。残すのはイベントごとの希望の人数・希望した回答の行番号・登壇ごとの人数だけで、名前・連絡先は残さない。アーカイブのイベントの画面に合計・登壇ごとの人数・元のスプレッドシートの行番号（「12行目・27行目」）と、名前や連絡先は保存していない旨を出す。登壇者へ伝える文の下書き（登壇者の名前・イベント名・人数だけ）をコードで作り、編集とコピーだけにする（送信しない）。登壇者ごとの満足度・不満は出さない（lib/casualInterview.ts、scripts/test_casual_interview.ts）
     - 回答のidは CSV の行番号から振る（例：ev019-r12）
   - アンケートの形はまだ分からないので、「全体の満足度＋自由記述」を前提にする。満足度の列は質問文で見分ける：登壇・発表・セッションを指していれば「登壇ごとの点数」、そうでなければ「全体の満足度」
   - コードの仕事：イベント単位の集計（回答数・全体の満足度の平均と分布）、登壇ごとの回答数、空欄や「特になし」の除外、登壇ごとの点数の列があるときだけその登壇の点数の集計と高い／低い（平均4.5以上／3.3以下）の洗い出し、感想を文に分けること、不満の原文の一覧、登壇者の記録に残す事実の文。全体の満足度は登壇者に結びつけない
   - AI の仕事：文ごとに「良い点／不満／どちらでもない」に分ける（点数が高くても不満が混ざる）、不満は「運営」か「内容」か・人を攻撃する言葉か、良い点のテーマ分けと代表的な声、登壇ごとの要約、次に聞きたいテーマのまとめ、別の社員のカードとの重なりの判断。AI に渡すのは集計結果と自由記述（文に分けたもの）と次に聞きたいテーマだけ（CSV全体・1件ずつの満足度・職種・個人情報は渡さない）
   - 呼び出しは「ネタ帳を更新」と同じ形：1イベント1回、保存前に検証して、だめなら差し戻す（最大3回）。検証：渡した文をすべて1回ずつ分類したか／不満に運営か内容かがあるか／良い点の文がどれかのテーマに入っているか・代表の声がそのテーマの文か／回答idが実在しその登壇への回答か／重なる先が別の社員の未発信カードか／要約・テーマ・内容への不満の一言に、攻撃の言葉や不満の原文・数字・内部の言葉が入っていないか
   - イベントのページ（イベントごと）
     - ネガティブ：原文に近いまま全部並べる。「運営（音響・時間・会場・配信など）」と「内容（難しい・速い・資料など）」に分けるだけ。同じ文はまとめて件数を出し、1件だけの声も落とさない。言い回しは和らげない（直すのは個人情報の削除だけ）。人を攻撃する言葉も出す（印を付ける）
     - ポジティブ：テーマごとにまとめて、件数（コードで数える）と代表的な声を1〜2件
     - コードで検査：AI が不満に分けた文が、画面の一覧に原文のまま全部出ていること
   - 書き戻し（コード）
     - 登壇者ごとの反応は内部の記録（data/talk_records.json）だけに置く。候補を出すときの参考として Agent に渡すだけで、画面用の窓口・Slack・下書き・カードには出さない
     - 登壇者の記録に入れるのは「内容（登壇）」だけ：反応のまとめ1行、登壇の中身の良い点のテーマと件数、内容への不満の事実（「前回は前提知識の多さを指摘する声が3件」。一言は AI、件数はコード）、回答数。点数は登壇ごとの点数の列があるときだけ（全体の満足度は入れない）
     - 運営・会場・設備の不満と良い点は、登壇者の記録とカードに一切入れない（イベントのページだけ）。まとめ・一言・登壇のテーマに運営・会場・設備の言葉があれば差し戻す
     - 内容への不満の原文は、イベントのページだけに置く
     - 人を攻撃する言葉は、登壇者の記録とカードに一切残さない
     - 次に聞きたいテーマは、登壇者のカードのテーマ案（未確認）に回す。勝手に確定しない
     - 別の社員の未発信カードと重なるテーマは、その社員のカードに「需要あり」として提案する
     - 見送った提案は、もう一度分析しても戻さない
   - 依頼から候補を出すとき、get_card・search_cards で、登壇者の記録（内部の参考）と採用済みの「需要あり」を文として渡す。登壇者の記録は候補を選ぶ判断の参考にだけ使い、理由・注意点・声かけ文に点数・不満・良い点を書かない。「需要あり」は推す理由に使ってよい。提案中・見送りの「需要あり」は渡さない
   - コードで検査：登壇者の記録に運営・会場・設備のこと・不満の原文・攻撃の言葉・イベント全体の良い点・全体の満足度が入っていないこと／カードに登壇者の評価が入っていないこと／画面用の窓口（イベント単位の集計）に登壇者ごとの評価が入っていないこと

### 人が直したカードの扱い（Human in the Loop）
- 技術広報は画面でカードを直せる。直したカードは「確認済み」になり、提案で優先して使う
- Agentが活動を読み直すとき、人が直した項目（要約・テーマ案・おすすめの形）は上書きしない
- 事実として決まる項目（根拠のidの追加・最新の活動日・発信状況）は更新してよい
- 新しい活動から別のテーマ案が考えられるときは、「新しいテーマ案（未確認）」として追加し、画面に印を付ける
- 新しい活動が別の取り組みなら、新しいカードを作る。確認済みの状態は外さない
- 作業ログに「確認済みカード：内容は変えず、根拠だけ追加」のように、何をしたかを出す

### 候補の出し方（自信のある候補と条件付きの候補）
- 技術広報は複数の候補から選ぶことが多いので、合う人がいるだけ並べる。上限は5人（lib/config.ts の MAX_CANDIDATES）。人数をそろえるために根拠の弱い人を足さない
- 順位はテーマの合い方と根拠（取り組みの中身・数字・本人が手を動かしたか）で付ける。登壇の経験（初登壇か、最近登壇したか）では順位を上げも下げもしない
- 自信のある候補（テーマに合い、断られる3つの理由にも大きな引っかかりがない）を先に出す
- 根拠はあるが引っかかる点がある人は「条件付きの候補」として、何が引っかかるか（予定が詰まっている・テーマが少しずれる・根拠が1件だけ など）を1文で明記して後に並べる
- 誰もいないとき（0人）だけ、「見つからない理由」と「次に確認すべきこと」を返す。1人以上いれば返さない
- 登壇経験の印：各候補に、コードが past_talk_count と last_talk_date から「初登壇」（登壇0回）・「半年以内に登壇」（最後の登壇が183日以内）・「登壇経験あり」（それ以外）を付ける（lib/talkTag.ts、`talk_tag`）。画面では理由の前に出す（Slack には候補を書かない）。偏りを減らすかどうかは、この印を見て人が決める
  - 前にコードが足していた注意点「最近登壇した（日付）」は、この印に置き換えた
- APIの返り値では、候補ごとに `confidence`（`"strong"` ／ `"conditional"`）と `caveat`（引っかかる点の1文。conditional では必須、strong では null）を持つ。自信のある候補が先、条件付きの候補が後の順に並ぶ
- 指名の依頼では、指名された本人を必ず候補に並べる。本人の根拠は依頼そのもの（`evidence_request_id` に依頼のidを入れ、`is_nominee: true`）
  - 本人が忙しい・予定が重なる・テーマが本人の取り組みとずれる場合は conditional にし、caveat に理由と代案（共同登壇やモデレーター役なら可能か など）を書く
  - 指名された本人以外は今の基準のまま（根拠がなければ並べない）

## カードの項目（data/cards.json）
- card_id、employee_id
- 取り組みの要約（2〜3文）
- 話せるテーマ案（1〜3個。本人の取り組みから絞った具体的なタイトル）
- 根拠（activity の id の一覧。実在するものだけ）
- おすすめの形（登壇／LT／ブログ）と理由
- 発信状況（未発信／ブログ済み／登壇済み）と published の id
- 最新の活動日
- 打診履歴（日付・依頼id・結果・理由）
- 作成日・更新日

- 確認状態（未確認／確認済み）と、人が直した項目の一覧
- 新しいテーマ案（未確認）：確認済みカードに対してAgentが提案したもの。採用・却下は技術広報が1クリックで行う。イベント後のアンケートの「次に聞きたいテーマ」もここに入る
- イベントの反応（v0.4）：需要あり（別の社員の登壇で、参加者がこのカードのテーマを聞きたいと答えた）。状態は提案中／採用／見送り。登壇者本人への反応（評価）はカードに入れない（内部の記録だけ）

### 発信済みの取り組みの扱い
- 発信済みでもカードは作る。発信状況を「ブログ済み」などにし、published の id を付ける
- 「公開しました」という告知の投稿は、取り組みの根拠ではなく発信の記録として扱う。告知の投稿だけで別のカードは作らない
- 「ブログのネタを出す」ではブログ済みのカードは出さない。登壇の提案では候補にしてよい（理由に「ブログの内容をLTにしやすい」と書ける）
- 評価の「未発信20件のうち15件以上がカードになるか」には数えない

## 受信箱と窓口（v0.3）
- 受信箱（data/inbox.json、実行時のデータなので git には入れない）
  - 依頼を受け取ったら、既存の依頼と同じ形で登録し、裏で候補づくり（既存の runAgent）を自動で始める
  - 状態：準備中（processing）→ 準備済み（ready）。失敗したらエラー（error）。準備中のまま15分を過ぎたもの（サーバーの再起動など）はエラーにする
  - 候補と作業ログを保存しておき、開いたときはそのまま出す（もう一度は実行しない）。「もう一度探す」で探し直せる
  - 指名の依頼で代わりの候補がいるときは、候補ができた時点で「準備済み」にし、代わりの人を推す文はそのあと裏で作る（lib/inbox.ts の prepare）。作っているあいだは pitch_status が pending で、文はまだない。できたら result.alternative_pitch と作業ログに入る。作れなくても候補は準備済みのまま（pitch_status が error、理由は作業ログ）。pending のまま5分を過ぎたら error として扱う
  - 入口は2つ：Slack（セッション②のボット）と、画面の「手で追加」（前の「依頼文を貼る」）
  - 承認・声かけ文の下書き・結果の書き戻しは、既存の流れをそのまま使う（受信箱の依頼の id で引ける）
- 窓口（形は docs/inbox-api.md。変えない）
  - POST /api/inbox：{ text, source: "slack" | "manual", meta?: { channel, ts, user, permalink } } を受け取り、{ id } を返す
  - GET /api/inbox/{id}：{ id, status, url } を返す。url は画面でその依頼を開くURL（?inbox={id}）。候補の名前・理由・件数・見つからない理由は返さない（Slack に出さないため。人選は技術広報が画面で見る）
  - localhost からのリクエストだけ受け付ける（開発サーバーは 127.0.0.1 だけで待ち受ける）
- ?mock では、保存済みの結果（docs/eval_latest.json → app/_client/proposals.json）を使い、受信箱に「準備済み」の依頼が並ぶ（APIを使わない）
- 受信箱の依頼の指名（v0.3.2）
  - 依頼を既存の形に変換するところで、依頼文から「指名された人」の名前を Agent が読み取る（小さな1回の呼び出し。新しい仕組みは作らない）
  - 読み取った名前が社員データに実在するかはコードで確かめる（フルネーム、または姓だけで1人に決まるとき）。決まれば既存の指名の項目に入れ、「指名された本人を必ず並べる」「代わりの提案」がそのまま効く
  - 実在しない・同じ姓が複数いて1人に決まらない・読み取りに失敗したときは、指名なしとして扱い、その理由を各候補の注意点に書く（候補がいなければ見つからない理由に書く）
- 窓口（受信箱）は送信しない。Slack への送信は Slack ボット（scripts/slack-bot.ts）が、依頼スレッドへの受付の返信と SLACK_NOTIFY_CHANNEL への通知だけ行う

## カード → 出し先を探す（v0.4）
- 「依頼 → 人を探す」（枠が先）の逆向き。ネタ（カード）が先で、社外の出し先を探す
- 新しい仕組みは作らない。Agentのループ（runToolLoop）・候補の出し方（自信のある／条件付き）・内部の言葉の判定・日付の判定・ブログ提案・声かけ文の仕組みを使い回す
- 入口：カード詳細の「出し先を探す」ボタン
- データ：data/external_events.json（実在する公開イベントの情報、2026-11-21時点）。ファイルを読むだけで、外部サイトにはアクセスしない
  - 項目：id, name, url, event_date, cfp_status（open／closed／unknown）, cfp_deadline, cfp_url, format, themes, audience, location, note, checked_at
- ツール：search_external_events(query, from, to)（テーマの言葉・開催日の期間で探す。締切済みは can_apply=false で返す）。ほかは既存の get_card・check_schedule・get_published・get_speaking_history
- Agent が返すもの
  - 外部イベント最大3件：発表タイトル案・理由・形式・締切・注意点・根拠（カードのもとになった活動の id）・自信のある／条件付き
  - ブログ案（既存のブログ提案を、このカード1枚に絞って使う。発信済みのカードは出さない）
  - 合うものがなければ、見つからない理由と次に確かめること
  - 選んだ出し先で、本人への声かけ文の下書き（既存の仕組みで、中身を「このネタで出てみませんか」にする。編集できる。送信ボタンは置かない）
- 必ず付ける注意点（コードで決めて、決まった文のまま入れる）
  - cfp_status が unknown：「締切は公式で要確認」
  - event_date が null：「開催日は要確認」（日付チェックの対象外）
  - 締切が14日以内：「締切が近い（M/Dまで、あとN日）」
  - 本人の予定が開催日の前後3日に重なる：「本人の予定が重なる（…）」
- コードでの検証（提出時に差し戻す）：締切済み（closed、または締切が今日より前）は出さない／イベントidが実在する／根拠はカードのもとになった活動の id だけ／条件付きには引っかかる点の文／内部の言葉がない／開催日として書いた日付が開催日と食い違わない
- アプリの「今日」は日本時間の実際の日付（lib/clock.ts の todayJst）。評価・テストだけ FIXED_TODAY=2026-11-21 で固定する（scripts/_isolate.ts。データの checked_at と同じ日）
- ?mock：保存済みの結果（docs/eval_latest.json の venue_cases → app/_client/venues.json）を再生する。結果のないカードは「見つからない」の画面を見せる
- 未対応（v0.4 では作っていない）：ネタ帳の更新時に、締切の近いCFPに強く合う未発信カードを受信箱に「出し先の提案」として入れる

## 画面（3つのタブ）
配置の決まりは docs/ui-guidelines.md。ここには「何がどこにあるか」だけを書く。
- 上部：アプリ名と、タブ3つ（受信箱／ネタ帳／アーカイブ）だけ
- 受信箱（最初に開く。依頼が届いたとき）：左に依頼の一覧（Slack・貼った会話・サンプルの依頼。状態の印つき。開催日が過ぎた依頼は出さない）、右に選んだ依頼（読み取った項目 → 作業ログ → 候補（0〜5人）→ 承認 → 声かけ文とLT構成案・主催者への返事の下書き → 結果の記録）。右上の「会話を貼って追加」から X の会話などを貼る
- ネタ帳（人を知りたいとき・ネタを育てるとき）：左に人の一覧（社員全員。絞り込み：未発信のネタあり／初登壇／事業部）、右に選んだ人（人の情報と直す、その人のカード、直近のブログ、最近の活動）。上に「ブログのネタを出す」「ネタ帳を更新」「アンケートの声」「担当者未定のネタ」
- アーカイブ（イベントが終わったあと）：左に開催日が過ぎた依頼と過去のイベントの一覧（アンケートの件数・分析済みか）、右に詳細。過去のイベントは、イベント単位だけを出す（回答数・全体の満足度、不満は運営・会場・設備／内容に分けて原文のまま、良い点はテーマごと、次に聞きたいテーマ）。登壇者ごとの点数・不満・良い点は出さない
- 候補はネタ帳のカードとして表示し、カードを開けば根拠の投稿と打診履歴が見える。カード詳細はどのタブからでも開ける
- 声かけ文と主催者への返事は編集できる。送信ボタンは置かない（コピーだけ）
- 窓口 GET /api/events/{id} が返すのは event・overview（イベント単位の集計：回答数・全体の満足度・良かった点のテーマ・改善点（運営・会場・設備／内容、原文のまま）・次に聞きたいテーマ）・speakers（誰が何を話したか：名前・所属・タイトルだけ）・source（取り込みの結果）だけ。登壇者ごとの点数・不満・良い点、不満がどの登壇への声かは返さない（「窓口に登壇者ごとの評価が出ない」の検査は窓口全体が対象）。登壇のタイトルは、アンケートの「どの登壇か」の列（名前「タイトル」）からコードで取り出す
- カード詳細に「イベントの反応」（需要あり）を出し、提案中のものは採用／見送りできる
- 金額（今回・累計）は通常画面には出さず、URLに ?debug を付けたときだけ上部に表示する（技術広報にはお金の数字は不要なため）。記録（data/usage.json）と自動切り替えはそのまま

## 使いやすさの原則
- 新しい入力を増やさない（結果の記録はボタンを選ぶだけ）
- 候補は合う人がいるだけ（5人まで）。理由は1行で、登壇経験の印が近くにあり、根拠にすぐ飛べる
- 声かけ文は自分の言葉に直して使える
- 「なぜこの人か」がカードでいつでも確かめられる

## 判断基準（指示文に入れる）
- テーマは、本人が実際にやった取り組みと、時流（例：今セキュリティが熱い）の両方から考える
- 順位はテーマの合い方と根拠で付ける。登壇の経験では順位を変えず、候補に印（初登壇／半年以内に登壇／登壇経験あり）を付けて人が選ぶ
- 断られる3つの理由（そのテーマなら自分ではない／時間的に厳しい／他のイベントと被る）を先に確認する
- 根拠にした投稿を必ず示す。根拠のない推測で人を推さない
- 使う人向けの文（要約・テーマ案・理由・注意点・引っかかる点・見つからない理由・次に確認すべきこと・声かけ文など）には、内部の項目名・値・id（reviewed=false、confidence、card_id、act088、e002 など）を書かない。人の名前・投稿のタイトル・日付と普通の言葉で書く。idは根拠の項目にだけ入れる
- 声かけは下書きまで。送るのは人
- 送ってよいのは、依頼スレッドへの受付の返信（「受け付けました。技術広報から連絡します」）と、SLACK_NOTIFY_CHANNEL（技術広報だけが入る非公開チャンネル）への通知（「新しい依頼の候補が準備できました」と画面へのリンク）だけ。候補の名前・理由・件数・見つからない理由は Slack のどこにも書かない。DM・別チャンネル・候補者本人への送信は作らない

## 承認ポイント
- Agentが自分でやる：検索する、読む、候補を考える、下書きを作る、依頼が来たSlackスレッドに受付の一文を返す、準備ができたら技術広報だけの非公開チャンネルに画面へのリンクを送る（候補の名前・理由・件数は Slack に書かない）
- 人がやる：候補を選ぶ、声かけを送る、結果を記録する

## 忙しさ（予定から計算）
- なぜ：前は架空データに「忙しさ1〜5」を決め打ちで書いていただけで根拠がなかった。断られる3つの理由の1つ「時間的に厳しい」を、予定という事実から出す
- 計算（lib/busyness.ts、コードだけ・AIは使わない）
  - 「今後2週間（今日から14日）の平日・勤務時間（10〜19時）のうち、予定で埋まっている割合」。週末と勤務時間の外は数えない。重なった予定は二重に数えない。終日の予定はその日の勤務時間をすべて埋める
  - 区分：4割未満は「余裕あり」、4〜6割は「普通」、6割以上は「詰まっている」
  - 返すもの：割合・区分・期間・期間内の予定の一覧（開始・終了・終日かどうかだけ。タイトル・場所・参加者は持たない）
  - 画面からは busynessFor(社員id) と busyText(結果) を呼ぶ
- 予定の出どころ
  - 架空の社員：data/calendar.json ＋ data/schedules.json。calendar.json の埋まり具合は、前の決め打ちの忙しさに近くなるように作った（デモの筋書き：e002・e015 は詰まっている、e012 は余裕あり、を保つため）。画面や Agent に出るのは、この予定から計算した値
  - 本人（DATA_SOURCE=github の e001）：予定データがないので「予定は不明」。数字は入れない。check_schedule も「予定は不明（本人への確認が必要）」を返す
  - 本物のカレンダー：CALENDAR_ICS_URL（iCal の URL、秘密）があるときだけ読む（今は本人1人分・DATA_SOURCE=github のときだけ）。読むのは開始・終了・終日かどうか・繰り返し（毎日・毎週）・中止・「空き」の印だけで、タイトル・場所・参加者・説明は読まない。読めなければ「予定は不明」。URL は表示・ログ・コミットしない
- 使い方
  - Agent：社員一覧・get_employee・search_cards・get_card に「予定の埋まり○%（区分）」か「予定は不明」を渡す。list_employees は忙しさの上限の代わりに予定の埋まり（%）の上限で絞る（予定不明の人は除かない）
  - 候補の注意点：詰まっている人には、コードが「今後2週間は勤務時間の○割が予定で埋まっている」を足す（前の「忙しい（忙しさN）」の代わり）
  - 声かけ文・代わりの人を推す文・ブログのネタ・出し先：予定の埋まりを言葉で渡す
  - 画面：「忙しさN」の代わりに言葉（例：今後2週間は勤務時間の7割が予定で埋まっている／予定は不明）。画面の配置は変えない
- 使う人向けの文の判定（lib/plainText.ts）に「忙しさ5」「忙しさが4」「予定の埋まり72%」を足した（提出時・カード保存・結合テストで差し戻す）
- テスト（APIなし）：npm run test:busyness（割合の計算、重なり、勤務時間の外、終日、週末の除外、区分の境目、予定不明、.ics の読み込み、iCal の設定があるときだけ使う）。.ics は架空のファイル（scripts/fixtures/sample.ics）
- 評価の正解（data/README.md）は変えていない。正解の説明は「忙しさ5」などで書かれているが、計算した区分でも同じ側になる（e012・e017 は余裕あり、e018 は普通、e002・e015 は詰まっている）

## 日程が未定の依頼で空いていそうな日
- なぜ：主催者の日程が決まっていない依頼（「2月か3月」「春ごろ」など）では、候補の人の都合のよさそうな日を添えると、主催者との日程調整が早く進む
- 読み取り（lib/intake.ts）：依頼の読み取りに「日程の手がかり」（date_hint）を足した。Agent には会話にある言い回しをそのまま返させ、本当に会話にあるか（20字まで）をコードで確かめる。なければ捨てる。日程が1日に決まっていれば使わない。Agent に渡す依頼文の先頭にも「日程：未定（時期の手がかり：「…」）」と書く
- 期間に直す（lib/dateHint.ts、コードだけ・AI は使わない）：決まった言い方だけ。「◯月」「◯月か◯月」「◯〜◯月」「上旬・中旬・下旬・末」「春（3〜5月）・夏（6〜8月）・秋（9〜11月）・冬（12〜2月）」「年明け・年末・年内」「来月・再来月・今月」。年は今日より後にくる年にし、始まりは今日より前にしない。分からなければ今日から8週間
- 空いていそうな日（lib/dateHint.ts・lib/dateSuggest.ts、予定は lib/busyness.ts）
  - 期間の中の平日で、19〜21時（.env の DATE_SUGGEST_START_HOUR・DATE_SUGGEST_END_HOUR で変えられる）に予定がなく、終日の予定もない日を最大3日。週ごとに最初の日を取り、週を均等に間引いて、なるべく週をばらす
  - 平日から、日本の祝日（振替休日・国民の休日を含む）を除く。一覧は lib/dateHint.ts に2026年・2027年の分を持つ（外部のサイトや API には取りにいかない）。一覧にない年が期間に入るときは「◯年の祝日は一覧にないので、祝日を除いていません」と補足する。年を足すときは一覧に1年分を足す
  - 年末年始（12/29〜1/3）も会社の休みとして除く（.env の DATE_SUGGEST_YEAR_END_OFF=off で除かない）
  - カレンダーがない人は出さない（「予定は不明」）。予定が分かる範囲より先の日も出さない（空いているとは言えないため）。架空データは calendar.json の最後の日（2026-12-31）まで、iCal は読んだ範囲（今日から183日）まで
  - iCal は空いていそうな日のために半年分を読むようにした。忙しさの計算は今までどおり今後2週間だけ
  - 年末年始の休みなどは、予定に入っていなければ空いている扱いになる（推測では除かない）
- 返すもの：候補ができたときに計算して受信箱に保存し、受信箱の詳細の窓口（boardDetail → detailView）の date_suggestions に返す。中身は、手がかり・期間・見た時間帯・候補ごとの日・補足・返事の1文の材料（「12月1日（火）・12月14日（月）あたりなら調整しやすそうです（本人に確認します）。」）。日程が決まっている依頼・候補がいない依頼では null
- 主催者への返事：1文は材料だけで、下書きには自動で入れない。入れるかどうかは技術広報が選ぶ。予定の中身や埋まり具合は主催者に出さない。今の検査（lib/organizerReply.ts）で確かめたところ、「終日の予定があり、夜は空いています」「出張」「午後に会議が入って」のような予定の中身が通ってしまったので、「予定の中身」の検査を足した
- テスト（API なし）：npm run test:datesuggest（期間への変換、終日の予定・夜の予定・週末の除外、週をばらす、時間帯の設定、カレンダーなし、予定が分かる範囲の外、手がかりの確かめ、受信箱への保存と詳細、返事の検査）
- 本番の確認（11/21、1回 $0.117・24秒）：日程が未定の架空の会話（「12月か1月ごろ」）で、手がかりを読み取り、期間は 2026-12-01〜2027-01-31。候補（百瀬 結衣）に 12/1・12/14・12/28 を出し、1月は予定が分からないので見ていないと補足した。結果は docs/date_suggest_result.json

## 元のデータと実行時のデータ
- 元のデータ：git に入っている data/ のファイル（架空の社員・活動・カード・読んだ記録、data/sources/ の取り込み結果、本人の初期のカードなど）。アプリは読むだけで、書き換えない

  - カード：元のデータと中身が違うカード・新しいカードだけを data/runtime/cards.json に書く（読み込みで補う空の項目は書かない）。消したカードは id だけ残す。本人（e031）のカードは DEMO_PERSON=on のときだけ見え、off のときに保存しても消えない

## ブログと Slack の一部（人を選ぶ材料）
- ブログ（lib/moreSources.ts）：data/sources/blog_posts.json。既存の published の「メンバーのブログ」8件と同じ記事（書き手・日付・タイトル・URL が同じ）に、本文の要約（3〜5文、架空）を付けたもの。活動の種類 blog（id は blg001〜）

- Slack の一部（scripts/slack/sources.ts、npm run slack:sources）：練習用ワークスペースの、.env の SLACK_SOURCE_CHANNELS に書いた公開チャンネルだけを読む（設定がなければ読まない。非公開・DM・グループDM は読まない）

  - 読むのは前回以降の投稿だけ（チャンネルごとに最後の ts を data/sources/slack_state.json に残す）
  - コードで落とす：ボットの投稿、参加・編集などの通知、スタンプ・メンションを除いて30字未満の投稿、対応表（data/sources/slack_users.json：Slack のユーザー id → 社員 id）にいない人の投稿。落とした件数と、対応表にいない人の Slack のユーザー id と件数を出す（名前は取らない）

## リリースノート（チームのネタ）
- 目的：プロダクトのリリースノートは「何を作り、誰の何を解いたか」がまとまっていて、登壇ネタの材料として濃く、量も少ない。これをネタ帳の材料に足す
- データ：data/sources/release_notes.json。バクラクの公開されているリリースのお知らせ（https://bakuraku.jp/news/）から、製品・機能のリリース10件（導入事例・イベント・調査・CMは除く）。公開ページを読むだけで集め、要約は原文を写さず自分の言葉で2〜3文。項目は id（rel001〜）・日付・プロダクト名・タイトル・URL・要約・担当チーム・担当者
  - 担当チーム・担当者は架空の社員への架空の割り当て（data/README.md に明記）。3件は担当者なし
- 活動として読む（lib/releaseNotes.ts）：type が release_note の活動として activities() に入る。根拠の参照元から公開ページ（url）に飛べる。リリースノート自体は「発信済み」ではない（登壇やブログはまだ）
  - 担当者（活動の author_id）は、技術広報の割り当て → データの担当者 → キーワード一致＋AI の判断 の順で決まる。どれもなければ空で、推測で埋めない
  - ネタ帳の更新（社員ごと）はリリースノートを読まない。別の流れでカードにする
  - 評価は RELEASE_NOTES=off で入れない（今までどおりの材料で判定）。DATA_SOURCE=github のときも入れない
- カードにする（lib/releaseCards.ts、npm run release:cards）：カードになっていないリリースノートだけを、AI への1回の呼び出し（差し戻しは最大2回）でまとめて「チームのネタ」にする（何を出したか・どんな課題を解いたか・話せるテーマ案・おすすめの形）
  - 担当者が分かるもの → その人の新しいカード。既存のカードは更新しない
  - 担当者がいないもの → 同じ機能に触れている活動を、コードでキーワード一致（一般的な言葉を除き、2語以上一致）で探す。候補がいれば、最後の判断だけ AI がする。AI が選んだ人は、候補にいて、その人の一致した活動を根拠に挙げたときだけ認める（コードで検査）。迷えば決めない
  - 決まらなければ「担当者未定のネタ」（data/unassigned_cards.json、card_id は card-team-01〜、employee_id は null）。カード（data/cards.json）とは分けて保存し、候補の検索（依頼 → 人）には出さない
  - 担当者が決まっていないリリースは、提案の候補の根拠にも使えない（提出の検査で差し戻す）
- 割り当て（技術広報）：POST /api/unassigned-cards/assign { card_id, employee_id } で担当者を割り当てると、その人の普通のカードになり、確認済み（reviewed）として扱う（Agent は文を上書きしない）。割り当ては data/release_owners.json に by="human" で残り、リリースの活動の担当者になる。一覧は GET /api/unassigned-cards（リリースノートのタイトル・URL つき）。画面（ネタ帳での一覧と割り当て）は別の担当
- 最初の実行（11/21）：担当者が分かる7件はカード、担当者なしの3件は同じ機能に触れている活動が見つからず担当者未定のネタ。$0.093
- テスト（APIなし）：npm run test:release（担当者なしを推測で埋めない、候補の外や根拠なしの選び方を認めない、根拠の id が実在する、既存のカードが変わらない、担当者未定のネタは候補の検索に出ない、割り当てで確認済みのカードになる など）

- 追記（見せる用を発表用とほぼ同じにする、11/22）：見せる用（SHARE_MODE=lan）でも「ネタ帳を更新」と「この依頼の記録」を使えるようにした（記録の中身は名前・時間・金額・成否だけ）。「ネタ帳を更新」は、1回の見積もりの上限（NOTEBOOK_BUDGET_USD、超えるなら始めない・途中で届いたら残りは次回）・二重実行の防止（動いている間の2回目は 409）・1人あたりの上限で守る。1人あたりの上限 SHARE_PER_PERSON_USD を足した：合言葉で入ったブラウザごとに使った API 代を数え（人の印のハッシュで data/runtime-share/person_usage.json に保存。印の値そのものは保存しない）、超えたらその人だけ API を使う操作を止めて「この端末で試せる分を使い切りました。保存済みの例（?mock）は引き続き見られます」を出す。裏で続く候補づくりの金額も、依頼した人に数える。合計の上限 SHARE_BUDGET_USD はそのまま（印を消せば数え直せてしまうため）。画面の右上に、その人の残り（「あと $3.20 分試せます」）を小さく出す（見せる用のときだけ）。発表用には効かない。人の見分け方は③の lib/visitor.ts（visitorKeyOf など）を使う。「依頼として進める」（/api/inbox/{id}/proceed）も API を使う操作として上限の対象に足した。見せる用でできないのは、Slack から依頼が届くことと ?debug だけ
- 追記（メンター用の合言葉、11/22）：見せる用の合言葉を2種類にした。MENTOR_ACCESS_CODE（任意、12文字以上・一般と別。一般と同じ守り：回数の制限・全体の上限・値を表示しない）で入った人にはメンターの印（cookie nb_role、合言葉から作ったハッシュ。合言葉を変えると前の印は使えない）を付け、1人あたりの上限を SHARE_MENTOR_USD（なければ一般と同じ）にする。一般は SHARE_PER_PERSON_USD のまま。画面には役割を出さない。役割は lib/personBudget.ts の roleOf(req)（要求から）・currentRole()（API を使う窓口と裏で続く処理の中）で分かり、使われた結果と実行の記録への role: "mentor" の付与と eval:from-feedback での選び出しは③が付ける。メンター用の合言葉は Notion に書かず口頭で伝え、Notion に書くのは見せる用（3100番）のアドレスだけ
