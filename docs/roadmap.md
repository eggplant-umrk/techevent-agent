今の作りは「1人の技術広報が、1台の端末で、JSON ファイルに保存して使う」前提です。ここに書いた作業は、どれも今日のデモには要りません。

- 今日までに済ませたもの：API を使わないテストを1コマンドで流す（`npm test`）、CI（`.github/workflows/ci.yml`）、文書の食い違いの直し、保存の入口の一覧（[docs/storage.md](storage.md)）、ネタ帳の更新で確認済みのカードを上書きしないことのテスト（`npm run test:reviewed`）

## 1. 保存の入口を1つにする（発表のあと）

- 今：JSON の読み書きが8か所に別々にある（[docs/storage.md](storage.md) の2）。どれも「全部読む → 直す → 全部書く」で、直接の上書き
- 困ること：dev サーバーと `npm run notebook` を同時に動かすと記録が消える。書いている途中で落ちるとファイルが壊れ、金額の記録が壊れると `totalUsd()` を使う窓口が全部失敗する。DB に移すとき、直す場所が8か所ある
- やること
  - 読み書きを1つのモジュールにまとめる（`lib/runtime.ts` の `readJsonFile`・`writeJsonFile` を土台に）。書き込みは一時ファイルに書いてから置き換える
  - 「カードを読む」「受信箱の1件を直す」のように、データごとの入口（関数）だけを外に見せ、ファイルの名前や場所は中に閉じる
  - テスト用の差し替え（`INBOX_FILE` など12種類）を、置き場所を1つ渡す形にする
  - `lib/data.ts` の「読むだけ」と金額の記録の書き込みを分ける
- 確かめ方：`npm test` が通る。docs/storage.md の2の表が1行になる

## 2. id の作り方を変える（発表のあと）

- 今：カード（`card-e012-01`）・担当者未定のネタ・Slack の投稿は「件数や最大の番号＋1」、GitHub の活動は「並び順」（docs/storage.md の4）
- 困ること：同時に作ると同じ id になる。GitHub を取り込み直すと番号がずれ、カードの根拠が別の活動を指す（id は実在するので検査を通る）。PR と Issue の検索は100件で打ち切りで、超えた分は黙って落ちる
- やること
  - 新しく作るものは、受信箱と同じ「時刻＋乱数」か UUID にする
  - 外から取り込むもの（GitHub・Slack）は、元の URL から決まる id にする（取り込み直しても同じ id）。今の id との対応表を1回作って、既存のカードの根拠を引き継ぐ
  - 社員 id を「e＋数字3桁」と決め打ちした検査（`lib/plainText.ts`）を、社員データに実在する id の一覧で見る形にする
  - GitHub の検索を、100件を超えても続きを読む形にする
  - GitHub の取り込みの課題は、まとめて 14 に書いた
- 確かめ方：同じ人のカードを同時に2枚作るテスト、取り込み直しても根拠が変わらないテスト

## 3. DB への移行（将来）

- 今：1 のあとも、保存はファイル。同時に書く・一部だけ読む・条件で探す、ができない
- 困ること（docs/storage.md の5）：2つ以上の書き込みをまとめて成功・失敗させられない（結果の記録、担当者の割り当て、アンケートの書き戻し）。金額の記録は API を1回呼ぶたびに全件を読んで書き、入口（`proxy.ts`）も API を使う操作のたびに全件を読む
- やること
  - 1 でまとめた入口の中身を DB に替える（外から見える関数は変えない）
  - 元のデータに実行時の差分を重ねる作り（`lib/runtime.ts`）をやめ、「取り込んだ材料」と「Agent と人が作ったもの」を別の表にする。デモの初期状態に戻す（`reset:demo`）は、後者を消すだけにする
  - 組になっている書き込みをトランザクションにする
  - 金額は追記だけの表にし、合計は集計で出す（月・会社・用途ごと）
  - 同期のファイル読み書きをやめる（重い読み込みの間、ほかの人の操作が止まる）
- 確かめ方：今のテストが、保存先を差し替えてそのまま通る

## 4. 候補づくりを別の仕組みで動かす（将来）

- 今：候補づくりは、応答を返したあと同じプロセスの中で続ける（`lib/inbox.ts` の `void prepare`）。指示文と予定のキャッシュもプロセスの中
- 困ること：再起動すると途中の仕事が消え、15分たってからエラー扱いになる。サーバーを2台にできない。ネタ帳の更新とアンケートの分析に「同じものは同時に1つだけ」の止めがなく、2回押すと2回分の金額がかかる（API を使う操作の全体は同時に2件まで、は 11/22 に入った。`lib/apiSlots.ts`）。ネタ帳の更新は1人ずつ順番で、300人で3〜5時間（docs/stress_report.md）
- やること
  - 仕事の列（キュー）と、それを処理する係を分ける。状態（待ち・実行中・終わり・失敗）は DB に持つ
  - 同じ依頼・同じイベント・同じ人の更新は、同時に1つだけ
  - ネタ帳の更新は並列か Message Batches で流す（最初の取り込みは100人で $83〜166 かかるので、数日に分ける。docs/cost_estimate.md）
  - 1人の失敗で残りの人が止まらないようにする（今は `messages.create` の例外で全員止まる）
  - ボットが止まっていた間の Slack の投稿を、起動し直したときに読み直す
- 確かめ方：実行中に係を止めて起動し直すと、仕事が続きから進む

## 5. 社員一覧を検索で絞る（将来）

- 今：社員一覧を丸ごと指示文に入れている（`lib/prompt.ts`）。300人で約1.8万トークン、3,000人ならその10倍。人の情報（意向・NGのテーマ）も最初のメッセージに全員分
- 困ること：依頼1件の金額と速さが、社員数に比例して増える（100人 約 $0.25、300人 約 $0.34。docs/cost_estimate.md）。予定の埋まり具合は指示文を作ったときの値のままで、古くなる
- やること
  - 指示文から社員一覧を外し、カードと活動の検索（`search_cards`・`search_activities`）で候補を絞ってから、その人の情報だけを渡す
  - カードの検索を、全件の文字の一致から索引（全文検索か埋め込み）にする
  - 主催者への返事の検査（全社員の名前を1人ずつ正規表現で見る）を、名前の一覧での一致にする
- 確かめ方：結合テストの想定候補が変わらず入る。社員数を10倍にした架空データで、依頼1件の金額が増えない

## 6. 会社の id を通す（将来）

- 今：データの場所が `process.cwd()` の下に固定（18か所）。設定は環境変数（35種類）で、1プロセス＝1社
- 妨げになっているところ
  - 指示文に「LayerX」が直書き（`lib/heavy.ts`・`lib/prompt.ts`・`lib/nominee.ts` など12ファイル）
  - 時流のテーマ（`lib/config.ts` の `TRENDS`）、祝日と日本時間、勤務時間（10〜19時）、夜の時間帯（19〜21時）が固定
  - Slack は1つのワークスペース、金額の上限と自動切り替えも全体で1つ
  - 人の情報（`people.json`）と担当者の割り当て（`release_owners.json`）が、データの切り替え（`DATA_SOURCE`）に付いてこない
- やること
  - 3 のあと、すべての読み書きに会社の id を付ける（1 でまとめた入口の引数にする）
  - 会社ごとの設定（会社名・時流・祝日と時間帯・Slack・上限・モデル）を、環境変数から会社の設定の表に移す
  - 指示文は会社名などを差し込む形にする（毎回同じ部分はキャッシュが効くように、会社ごとに固定）
- 確かめ方：2つの会社のデータを入れて、片方の検索・候補・金額にもう片方が出ないことのテスト

## 7. 利用者と権限（将来）

- 今：「誰が使っているか」がない。合言葉は全員共通で、操作の記録も、役割ごとの見え方もない。「人を評価する情報は技術広報だけ」は、ネットワークの入口（`proxy.ts`）だけで守っている
- やること
  - 会社の ID 連携（SSO）でログインし、役割（技術広報・見るだけ・本人）を持つ
  - 誰が何を見た・直したかの記録
  - 社員本人が、自分の何が読まれているかを見られて、断れる入口
  - 保存するデータの保持期間（受信箱の本文、Slack の投稿者 id、アンケートの回答）
  - 本物のカレンダーは、1人ずつの iCal の URL ではなく、会社の連携で読む

## 8. 入力の検査と型（発表のあと）

- 今：窓口の入力を、型の言い換え（`as`）だけで受けている箇所が13。`zod` は依存に入っているが、どこからも使っていない
- 困ること：`/api/venues/draft` の `cautions` は型も長さも見ない。形の違う入力で 500 になる窓口がある（`/api/draft` の候補の引き直しと、受信箱のリンクの検査は 11/22 に直した）
- やること：窓口ごとに入力の形を1か所で決めて検査する（`zod` を使うか、依存から外すかを決める）。保存済みのものは id で引き直す形にそろえる
- あわせて：リリースの保存（`lib/releaseCards.ts`）は検査と保存で見ている項目が違い、欠けた提出だと保存の途中で例外になる

## 12. 速さと金額の残り（将来）

- `activities()` は呼ぶたびに5つの材料を読んで合わせる。`lib/blog.ts` はカードごとに呼び直す。`runUsd`・`totalUsd` は毎回金額の記録を全部読む。`/api/state` は毎回全員分の前処理をする → 3 と一緒に、読む範囲を絞る
- 1回の呼び出しの固定分（考える分 約1千トークン）が、活動の少ない人では金額の約4割（docs/cost_estimate.md）→ 新しい活動がたまった人だけを流す、軽いモデルで先に「カードにする中身があるか」を見る
- アンケートの指示文のキャッシュは日付が変わるまで作り直さない。その日のうちにカードが増える・発信済みになると一覧が古く、差し戻しを無駄に使う

## 13. 見せるとき・安全の残り（発表のあと）

11/22 に直したもの（見せる用と発表用を分ける、上限の必須、API を使う操作は同時に2件まで、合言葉のあとの移動先、提出の中身を作業ログに流さない、受信箱のリンク、`/api/draft` の引き直し）は、ここから外した。残り：

- 見せる用と発表用は、同じ端末の別のプロセスで、置き場所を分けているだけ（`data/runtime-share/`）。会社や利用者ごとに分ける作り（6・7）ができたら、その仕組みに寄せる
- 主催者への返事に渡す「確かめた項目」（イベント名・主催者の名前、120字まで）にも、短い指示は入りうる（docs/injection_check.md の残り）
- 落とす条件が広い（`lib/notebookPrep.ts`：`lint`・`deps`・`bump` がメッセージのどこにあっても落とす）
- アンケート：同姓の登壇者の突き合わせ（`lib/surveyCsv.ts` は姓の前方一致で、同姓がいると先の人に付く）。「10」を1と読む点数（11/21 の点検の指摘。直ったかは確かめていない）
- GitHub の取り込み：メンションの置き換え漏れ（「、@name」の形）

## 14. GitHub の取り込み（発表のあと：id ／将来：残り）

今の取り込み（`scripts/import_github.ts`）は、開発者本人1人の公開リポジトリを、トークンなしで読む作りです（`/users/<名前>/repos?type=owner`）。会社で使うには、次の5つが足りません。

| 課題 | 今 | 困ること | やること |
| --- | --- | --- | --- |
| 取り込み直すと根拠がずれる | 活動を日付とタイトルで並べ、並び順で `act001` と振る（295行）。リポジトリの紹介の日付は最後の push の日なので、push のたびに位置が変わる。コミットは1リポジトリ12日分まで（23行）で、その窓も動く | もう一度取り込むと、カードの根拠と「読んだ記録」が別の活動を指す。id 自体は実在するので、検査を通ってしまう | PR 番号・Issue 番号・コミットの日付など、元から決まるものから id を作る（例：`gh-<リポジトリ>-pr-123`）。今の id との対応表を1回作り、既存のカードの根拠と読んだ記録を引き継ぐ（2 と一緒に） |
| 活動の種類が粗い | 既存の4種類に合わせるため、リポジトリの紹介（README）と Issue を `design_doc`（設計メモ）に、PR とコミットを `github_pr` に寄せている（200・241・267・279行） | 画面の根拠に「設計メモ」と出るが、中身は README や Issue。AI も設計の文書として読む。Issue（困りごと）と README（紹介）は、ネタとしての重みが違う | 種類を足す（リポジトリの紹介・Issue・コミットのまとめ）。画面の表示名と、ネタ帳の更新の指示文での扱い（紹介だけではカードにしない、など）を種類ごとに決める |
| 同じ機能の PR をまとめずに AI に渡している | 1人の活動を新しい順に60件・2万字まで、1件ずつ並べて渡す（`lib/notebookPrep.ts`）。同じ機能の PR が10件あれば10件とも渡る | 金額が件数に比例する（活動1件 約 $0.0023。docs/cost_estimate.md）。AI が同じ取り組みを別のカードに分けたり、小さい PR を根拠にしそこねたりする | 渡す前にコードでまとめる：リポジトリ・ラベル・ブランチ名の先頭・関連する Issue・期間の近さで束にし、束ごとに「何件・いつからいつまで・主な PR のタイトルと本文の冒頭」を渡す。根拠の id は束の中の PR をそのまま使う（参照元へ1回で飛べるように） |
| 会社の非公開リポジトリが読めない | 公開リポジトリだけ。任意の `GITHUB_TOKEN` は個人のトークンで、制限にかかったときだけ使う | 会社の取り組みの大半は非公開リポジトリにある。個人のトークンで読むと、その人が見えるものが全部読めてしまい、誰が許可したのかも残らない | 組織の管理者が入れる GitHub App にする（読むリポジトリを組織が選ぶ、読み取りだけ、いつでも外せる）。読んだリポジトリの一覧を技術広報の画面に出す。会社ごとの設定（6）と、本人が断れる入口（7）のあと |
